# Native development fixtures

The seed command runs only against an empty loopback database after platform installation.
It does not reset a database. Bootstrap accounts, the registered platform-scope system
workload principals and reserved owner rows are excluded from the empty-target probes.
Other service principals are not exempt; any unrelated Auth account or concrete catalog/platform identity refuses
the run before fixture writes begin.

Fixture references are prepared in memory and then inserted into their actual owners. There
is no stored placeholder, universal Unit parent, or identity inferred from an arbitrary public
Entity. Human fixture accounts create an explicit native public Entity, institutional
representation and private main-identity choice. A retained Self association supports
older consumers; it is not the authority for native Realm enrollment. Other catalog
Entities remain independent catalog records; an Auth operator is recorded separately
when writing them.

## Native participation scenarios

The loader creates real synthetic sessions and uses native identity, consent, approval,
rule-acknowledgement and mute commands in its owner transaction. Content copy/history
uses the configured reference time; credential and enrollment effects use the current
database clock. Session tokens are random and are not printed. Fixture accounts are
eligible while authored effects are created; the declared nine unverified-account
examples are applied afterward as verification withdrawal. Governance scenarios remain
separate later effects.

Only approval-policy Realms have pending applications. Muting preserves the active
shared admission and records separate enforcement. Rule acknowledgement precedes join
when selected, so the admitted generation retains the exact revision and language.
Each Realm includes at least 15 acknowledged active examples; required join rules can
add more than the 180-example coverage floor. Read-only presentation views have no seed
writer. The seed verifier checks native consent, exact receipts/generations, pending
policy, independent mute, required rules and private main choices.

Native authority readers require READ COMMITTED. A transaction-scoped seed-run lock
serializes empty-target admission between seed processes, and nested service calls use
the same transaction. Run this offline with application writers stopped; the seed lock
is not a global application write lock. A failed fixture transaction rolls back its data.

Authored book content uses a native Publishing Text Version. Explicit synthetic Work and
Publication resources and coverage edges exercise the shared book model. Software revisions
use Software Versions, release membership uses Software Release components, and ordered
series membership uses Grouping relations and order profiles. System requirements use a
reviewed typed Catalog property. These replace the retired generic Variant, Release, Series,
and software-requirement rows.

Catalog titles and their changes use native Named Forms and immutable name revisions.
Rich fixture presentation remains in the shared localization capability attached by concrete
owner references. Platform content retains platform revision/restore examples. Favorites use
the Auth-owned service and history; ordinary private Collections have independent identities.

## Bounds and qualification

This is a one-time developer fixture workload, with zero production corpus rows or recurring
production work at both 500 million and 3 billion corpus rows. The current plan prepares fewer
than 10,000 identities; allocation refuses that ceiling. Primary fixture addresses depend on
owner and source key, independently of randomized Auth IDs and generated copy. The transaction
verifies that every prepared identity was materialized under its declared owner.

Empty-target admission performs at most one bounded existence probe per registered owner and
one Auth-account probe. Verification loads at most 10,001 IDs per owner and aborts as soon as
the total exceeds 10,000. It never materializes a production corpus in process memory.
Native commands retain their own batch, revision, reference, and byte budgets. Increasing
fixture bounds requires reviewing transaction time, generated relation counts, memory, and
test duration. This loader is not a production importer or production capacity qualification.

## Qualification checkpoint

The 2026-09-20 [native seed checkpoint](../../../../../docs/testing/database/native-seed-integrity-evidence.json)
records successful demo population, derived projection rebuilds, native seed
postconditions and aggregate reconciliation. The 50 accounts retain native identity
receipts and main choices; 290 enrollment heads include 16 approval-pending
applications, 48 independent mutes and 202 exact active-generation rule consents.
The preflight rejects unrelated human/service principals and a second seed run,
while retaining the three installed platform system duties.

Coverage remains required. It reaches governance and then fails because
`content_report.reported_revision_id` and the report service still require the
retired common revision model for catalog targets. This is a native governance
consumer gap, not a reason to remove catalog examples or change coverage into demo.
The failed transaction rolls back. [Known failures](../../../../../docs/testing/known-failures.md#native-seed-and-report-revision-evidence)
owns its reproduction and closure requirements.

Aggregate audits use concrete Post lifecycle, Auth-owned notifications/conversations
and canonical Favorites references. The removed chapter-count/progress aggregate
query addressed two tables absent from the current baseline, schema and writers;
localized book metrics remain checked. Chapter/progress product acceptance belongs
to its native content and reading owners. The broad corpus workload and recovery
claims remain unqualified by this bounded fixture.
