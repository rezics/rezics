# Music release source publication

Release intake, proposal application and withdrawal are queued operations. HTTP admission stores the exact source/proposal identity and current Participation authority and emits an operational task; it does not download archives or mutate track lists. Initial intake requires a direct account. Proposal grants retain their exact target and proposal scope.

The worker first verifies immutable archived snapshots, then prepares referenced identities in pages of 128. The source job stores the next dependency position and a generation. Initial reference preparation creates no release root. Update preparation records both incoming and previous-snapshot dependencies, so later compensation has exact authority evidence. These references are independently admitted native objects; their creation is not presented as an atomic release update.

Publication locks and revalidates the job, source binding, proposal, Participation authority, owner revision and exact component heads. All native release rows, reorder positions, histories, source occurrences, application journal and terminal receipt commit in one PostgreSQL transaction. SQL pages are at most 128 rows or 2 MB. They are not separately committed. The source writer validates the entire operation set before reallocating positions, which permits reorder cycles crossing page boundaries. Withdrawal uses the same path with the immutable before/after journal; a changed child head rejects the complete compensation.

Pause and publication serialize on the source/job locks. A completed pause fences old deliveries by generation. Resume revalidates the current operator and creates a fresh task generation, retaining already verified snapshot and dependency progress. A pause racing an already committing publication may observe the completed result. It does not retroactively undo a commit.

## Admission and execution limits

- Source bytes: 8,000,000 bytes per archive, independently of native changes. Two archives can be read for an update.
- Source structural occurrences: 16,384 per snapshot, including medium, track, identifier, TOC association, release event and label occurrences.
- Actual native component changes: 32,768, sufficient for the complete old-plus-new union within that occurrence bound. Unchanged source rows do not consume this mutation count.
- Ancillary name, semantic and identifier journal changes: 128. A larger journal is admitted only for one Music owner and its supported ancillary families; other mappers keep their ordinary bound.
- Newly created credit fragment/member and TOC/offset rows: 16,384. These are counted separately from structural changes.
- Dependencies: 16,384 distinct identities per snapshot, prepared 128 per task. Incoming and previous evidence occupy disjoint position ranges. Native authorization queries filter the actual requested targets before their bounded read.
- Native comparison and history bodies: 32 MB each. Current native values are loaded only for changed source components; full lifetime histories are never loaded.
- Each prepare/publish transaction has a 25 s PostgreSQL transaction deadline, 10 s statement deadline and 5 s lock deadline. A task lease is 30 s, with at most 10 committed claims and a 24 h task deadline. Claims commit before archive I/O, so a crash cannot erase consumed attempts. Expired leases cannot publish.
- The existing delivery policy limits concurrent handlers to four, outstanding deliveries to 64 and each transport envelope to 64 KiB. Queue admission consumes provisioned operational capacity credits. Source bytes and native arrays are not embedded in outbox messages.

Exceeded capacity is a persisted `blocked` result; exhausted attempts are `failed`. Neither advances native source authority. The constants are operational admission limits, not native schema cardinality limits. Arbitrarily larger documents remain outside this mapper's current admission contract; no partial release application is substituted for a successful result.

## Workload and growth

MusicBrainz's live [Bach 333 release](https://musicbrainz.org/release/d996abaa-ce14-45c7-944a-9c62adee19fe) was checked on 2026-09-08 through [WS/2 recordings and media](https://musicbrainz.org/ws/2/release/d996abaa-ce14-45c7-944a-9c62adee19fe?fmt=json&inc=recordings+media): 223 media, 5,532 tracks and 2,290,471 serialized UTF-8 bytes. This proves the former 128-row and 4,096-occurrence limits did not cover a real box set. It is not evidence that the much richer lookup including nested relationships fits 8 MB. The qualification fixture can reproduce the measured media/track cardinality, including CD offsets and shared printed credits, without treating synthetic timings as a production benchmark.

Let D be distinct dependencies, S source occurrences and C changed components. Correspondence planning is O(S), using track and medium indexes in memory bounded by the admitted archive. Dependency preparation performs O(D/128) bounded transactions. Publication uses O((S+C)/128) SQL pages plus bounded owner metadata work and database row triggers. Child head, history, correspondence and journal reads use source/owner-leading keys, with no global scan, deep offset or growing history walk. A popular release serializes on its owner/source locks; independent source buckets can be assigned to additional workers. Queue credits and lock/transaction timeouts provide backpressure rather than an unbounded in-process backlog.

For corpus planning, 500,000,000 occurrence rows at an illustrative 400-byte heap/TOAST average and 160 bytes of indexes are about 280 GB; 3,000,000,000 rows are about 1.68 TB, before WAL, replicas, free space and backups. With 64 hash partitions those averages are 7.8125 million and 46.875 million rows per partition. Actual UTF-8 names, source JSON and index bloat must be measured; these estimates are not measured capacity. An illustrative 256-byte journal row plus indexes is 128 GB / 768 GB at those cardinalities. Job rows include authority JSON and reverse FK indexes and must be budgeted separately; they are not held in process to schedule work. Old job/receipt retention requires an explicit archival policy compatible with immutable application evidence.

One full box-set update can write roughly two source supports per track, one or two component histories per changed track (reorders also create an intermediate head), one journal row and source baseline updates per changed component, plus native/index/WAL work. At 1 such release/s, thousands to tens of thousands of row operations/s must be provisioned; four workers do not establish that throughput. Production qualification must measure WAL volume, lock wait, p95/p99 transaction duration and queue credit occupancy on the expected hardware and distributions. Sustained pressure requires more source-bucket workers and database shards with explicit placement of an entire release and its histories; raising per-handler concurrency does not remove a hot-release lock.

## Deterministic qualification

`services/main/scripts/check-music-release-jobs.ts` runs only against an explicitly identified disposable loopback Atlas database. Its default is 260 tracks. Set `REZICS_MUSIC_RELEASE_JOB_TRACKS=5532` and `REZICS_MUSIC_RELEASE_JOB_MEDIA=223` for the measured box-set cardinality. It verifies committed staging, pause/resume, invisible initial root, exact native identifiers, an injected failure after earlier native mutations, rollback of all component/history changes, replay, cross-page reorder, complete journal, exact withdrawal, authority revocation, and a one-field update on a large otherwise unchanged snapshot.

The script retains only its newly admitted fixture rows. Its injected failure trigger targets only the new fixture release and is removed in a finally block. It does not reset a database or infer acceptance from a small fixture. The 25 s final transaction is the actual execution gate; a timeout is a failed qualification, not a reason to silently increase the deadline.

PostgreSQL's [transaction guarantees](https://www.postgresql.org/docs/18/tutorial-transactions.html), [row locking](https://www.postgresql.org/docs/18/explicit-locking.html), and [transaction/statement timeouts](https://www.postgresql.org/docs/18/runtime-config-client.html) define the publication boundary and cancellation behavior.
