# Native child source journals

`catalog-child-source.ts` upgrades the existing Program and Publishing component source occurrence families with an exact mapping/correspondence epoch, pure observed fields and native immutable history. It adds an application journal and current compensation baseline per owner. Fixed subtype rows retain their separate required-row source protocol.

A source-created child has a nullable pre-insertion history. Removal and withdrawal preserve the retained component head. Existing unrelated native children require an explicit reviewed correspondence; matching field values alone never transfer ownership. Three-way field updates preserve unobserved native values and reject conflicting edits. Source disappearance is refused when any surviving native field differs from the pure source interpretation, even when a later source edit has advanced that child's head. Withdrawal requires the exact post-application child history and restores the whole preceding native state through the invariant-enforcing command.

Parent references for historical serial installments point to retained component heads rather than mutable installment rows. This lets valid child-first removal retain historical evidence without blocking deletion merely because a historical source named the parent. Source target, publisher, area and vocabulary references have concrete native foreign keys; source values are not an unvalidated external-ID graph.

Every call handles at most 128 child changes and two recorded source epochs. One source object's high fan-out must use staged proposals instead of raising this bound. Typical planning assumes 5 children per source object, a 95th percentile of 64 and a maximum atomic proposal of 128 changes. Each accepted child write adds one native row revision and head update, one immutable source occurrence when the snapshot changes, one application row and up to two baseline updates. Contending writes serialize at the owner revision; import workers must limit concurrent proposals and observe owner/pool wait time rather than buffering unbounded work.

At 500 million occurrence/application rows, a planning allowance of 512 bytes of fixed tuple and short-source JSON plus 256 bytes of indexes is 384 GB per growing family; at 3 billion rows it is 2.304 TB, before replicas, retained snapshots, WAL, vacuum headroom and backups. Baselines scale with admitted source/owner/component identities; application history scales with accepted edits and withdrawals. Actual JSON can reach 1 MiB and dominates that estimate when large text is frequent, so monitor p50/p95 value bytes and total retained history. Parent registration uses 64 source-record hash partitions: average 7.8 million and 46.9 million rows per partition at the two cardinalities. This is placement/capacity math, not proof of production throughput.

Expected workload starts at 100 accepted child writes and 1000 bounded owner reads per second across independent owners. Target p95 is 200 ms for short owner writes excluding lock contention; sustained owner wait above 100 ms or pool exhaustion requires admission throttling. No whole-corpus scan or periodic recomputation is introduced. Native/history/source keys remain index-selective at both corpus sizes. Sharding must co-locate each source epoch/journal and preserve native-reference validation through a separately qualified cutover; these local checks do not certify billion-row operation.
