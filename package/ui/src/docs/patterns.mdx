# Patterns — Do / Don't

Code-level patterns. The "why" lives in [Voice](?path=/docs/foundation-voice--docs); the "what" lives in [Tokens](?path=/docs/foundation-tokens-colors--docs). This is the "how it should look in JSX/CSS".

This page is the human-readable counterpart to `.claude/skills/rezics-design/patterns.md`.

## 2. Cards (book / item / post)

Use shadcn `<Card>` as the canonical Rezics card primitive. Card semantics come from the domain component (`BookCard`, `PostCard`, `ArticleCard`); the primitive only controls surface policy.

| Surface | Visual read | Use |
| --- | --- | --- |
| `plain` | Same as page, no outer border or shadow; `interactive` reserves an outer hover state layer | Flat feed/media/list items |
| `contained` | Tonal fill without border or shadow; `interactive` adds tonal hover | Default panels and compact information cards |
| `elevated` | Same-color card with calibrated `elevation={1..10}` shadow; `interactive` adds hover lift | Media-rich recommendation and article cards |

Image, title, author — that's the card. The cover art carries the visual weight. Whisper border for table-row separation is fine; it's containment, not chrome.

## 5. Links

`<SafeLink>` classifies external URLs and routes them through a confirmation modal. App-route navigation is injected by the host shell with `linkRenderer` when SPA behavior is needed. Enforced by R5 and R13 in `bun run check:convention`.

```tsx
// Do
import { SafeLink } from '@rezics/ui';
<SafeLink href={url}>Read on Goodreads</SafeLink>

// Don't — raw <a> fails check:convention
<a href={url}>Read on Goodreads</a>
```

For in-app navigation, app/admin wrappers may pass their router link renderer to `<SafeLink>`. Core `@rezics/ui` exports do not import a router directly.

## 6. Icons

`lucide-react` is the canonical icon library; `@tabler/icons-react` covers the few glyphs lucide lacks (numbered circles, regional alpha, etc.). See `.claude/skills/rezics-design/icons.md` for the canonical mapping. Emoji are content — what users post — not UI vocabulary.

```tsx
// Do
import { Bookmark, Heart } from 'lucide-react';
import { Button } from '#/shadcn/button';
<Button variant="ghost" size="icon"><Bookmark size={20} /></Button>
<Heart size={16} fill="currentColor" />

// Don't
<button>📚 My Library</button>
<span>❤️ Like</span>
<svg viewBox="0 0 24 24"><path d="..." /></svg>  // no theme integration
// import from the MUI icons package — removed; use lucide-react
```

## 9. Spacing

UnoCSS `p-N` = `N × 4px`. Stay on the 4-pixel grid; don't escape with arbitrary px.

```tsx
// Do
<div className="p-2 gap-4" />

// Don't
<div className="p-[13px] gap-[22px]" />
```

If the closest token feels wrong, propose a token addition — don't bypass.

## 10. Mode (light / dark) handling

Tokens auto-switch via `<html class="dark">`. Never branch on theme mode in component code — let CSS variables resolve.

```tsx
// Do — works in both modes, no branching
<div className="bg-surface-base text-text-primary">
  <p>Auto light/dark.</p>
</div>

// Don't
const { resolvedTheme } = useTheme();
const bg = resolvedTheme === 'dark' ? '#1a1a18' : '#f5f4ed';
<div style={{ background: bg }} />
```

If a token doesn't exist for what you need, propose a token — don't branch on mode.

## 11. Mock data convention

Frontend-First development: mock the data and move forward. Annotate every placeholder with `// MOCK:` so `grep -r "// MOCK:"` finds them when the backend lands.

```ts
// Do
// MOCK: view count derived from book id hash
function mockViewCount(id: string | number): number {
  return (hashCode(String(id)) % 5000) + 10;
}

// MOCK: deterministic placeholder reviews until /api/reviews is implemented
const mockReviews: Review[] = [/* … */];

// Don't — silent placeholder, impossible to find later
const reviews: Review[] = [{ id: 1, title: 'Great book', body: '…' }];
```

## 13. Abstraction vs Split

When two components look similar, the question is whether they're the same
component with a variant prop or two distinct components that happen to share
metadata. Three tests, applied in order:

### Layout test

Do the two render trees differ structurally? Different children, different
slots, different number of regions? **Split.** A `variant` prop that flips the
JSX tree based on its value is the prop trying to tell you it shouldn't exist.

### Naming test

Could the variants share *one* name without a qualifier? `Default / Compact /
Large` — yes, that's a size axis on one component. `Hero / Sidebar / Inline` —
no, those are three different components doing three different jobs.

### Evolution test

If the next feature requires a new sub-region for one variant only, will the
prop API still feel like one component? If you'd add `showHeader`, `headerSlot`,
`headerVariant` to satisfy one variant, **split** before that grows.

### 10-second heuristic (story names)

Look at the story names you'd write:

- `Default / Compact / Small / Medium / Large / LongContent / LocaleCJK` →
  variant prop on one component.
- `Hero / Compact / Sidebar / Inline / Embedded` → these are different
  components; the words name *what they are*, not *which mode they're in*.

### Examples

The four split-vs-variant verdicts above all come from the same three tests:
**look at the layout, look at the names, look at how the next feature would
land**.
