# History Infrastructure — Design Plan

**Status**: Draft plan, pre-proposal  
**Date**: 2026-04-17  
**Scope**: Platform-wide content versioning system for wiki-style collaborative infrastructure

---

## 1. Context & Motivation

Rezics provides content infrastructure — a knowledge base whose content is editable by many users in a wiki-like fashion. The infrastructure is expected to grow toward a full wiki capability (via future Post extend), and most Unit types already exhibit collaborative-editing semantics (Book metadata, Chapter indexes, Attribution, Tags).

Today, all mutable fields on `Unit` and its extension tables rely solely on `updatedAt`. There is no record of prior state, no attribution of who made which change, and no mechanism to recover from vandalism or accidental overwrites. As collaborative surface grows, this gap becomes a liability.

This plan describes a **history infrastructure** that covers the platform's mutable content with appropriately different strategies per data shape, without incurring the complexity of full Wikipedia-style history (diff UI, revert UI, moderation workflows). The infrastructure is designed to be evolvable — capturing the hard decisions now, deferring UI/tooling until concrete product needs emerge.

---

## 2. Core Philosophy

Five principles emerged from the design discussion and govern every decision that follows.

### 2.1 Storage model determines mutation model

Two content categories exist, and they are fundamentally different:

| Aspect | Snapshot content (editorial) | Diff content (BookIndex) |
|---|---|---|
| Unit of storage | Each row is a complete state | Each row is a change |
| Deletion safety | Safe — rows are independent | Chain-breaking — never delete |
| Natural revert | Reload past state, save it again | Emit counter-diff events |
| Dedup model | Content-addressed hash | Event payload inline |

Treating both the same way — applying snapshot strategies to diff content or vice versa — produces designs that are either wasteful or broken.

### 2.2 Each aggregate owns its own history

A Unit's history contains only its own structural changes. References to other Units are stored as IDs. Displayed names, avatars, and other renderable data are resolved at render time from the main database. If an author renames themselves, that event lives in the author's own history — not in every book that references the author.

This avoids temporal joins, denormalization hell, and the GDPR nightmare of having to scrub PII from every snapshot that transitively referenced a deleted user.

### 2.3 Snapshot granularity ≠ database aggregate

A "Book" is not a single aggregate for versioning purposes. It is decomposed into sub-aggregates that have different edit rhythms:

- **Editorial** (title, description, attribution, tags, Unit core fields): low-frequency, wiki-style, snapshot per edit.
- **BookIndex** (chapter structure, forest of inline chapter data): high-frequency (1000/year normal for web novels), event-sourced.
- **Engagement** (reactions, scores, tag voteCount): not versioned — these are not editorial state.
- **Membership** (ShelfItem, tag memberships, RealmUnit): events-only if recorded at all.

### 2.4 Revert is not a first-class operation

For snapshot content, revert is just a normal edit that happens to produce a state equal to a past one (content-hash dedup makes it storage-free). For diff content, revert is a batch of regular edit events generated by a tree diff algorithm. Neither case requires a dedicated `REVERT` operation in the data model. This eliminates a whole class of edge cases (concurrent edits with revert, nested reverts, revert semantics ambiguity).

### 2.5 Bot is user

There is no actor taxonomy (HUMAN/BOT/SYSTEM). Every event, revision, and audit log record carries a single `userId` column. Bots and system processes have User records and are subject to the same permission system, rate limits, and moderation tools as any other user. This eliminates parallel code paths and makes the audit trail uniform.

## 3. Scope & Goals

### 3.1 In scope

- **Editorial history** for Units that opt in (by type) — full snapshots per edit, indexed by revision.
- **BookIndex history** — event-sourced with periodic snapshots for fast state reconstruction.
- **Audit log** — minimal "where" record linking edits to their snapshot/event and actor.
- **Reference resolution contract** — shared types defining how dangling/deleted/restricted references are displayed.
- **Rollback UX** — moderators can roll back BookIndex to a prior point; for snapshots, moderators reload and save.
- **Snapshot deletion** — admins can prune editorial snapshot rows.
- **Universal history link** on every Unit card in UI.

### 3.2 Explicitly out of scope (for v1)

- Proposal/approval moderation workflow (Wikipedia-style edit-review queue).
- Diff UI (semantic diff rendering of changes).
- Surgical (cherry-pick) revert for BookIndex — rollback is the only supported revert semantic.
- Retention policy automation (tiered retention across ages).
- Compliance payload scrub implementation (design position preserved, not built).
- History for engagement data (reactions, scores, tag voteCount).
- Cross-aggregate revert (rolling back a book also affects comments, etc.).

### 3.3 Initial data scope

- ~1M verified books imported from the old platform as initial assets.
- Additional content flows in organically via the `dispatch` crawler infrastructure pulling metadata from legitimate sources.
- Long-term horizon: millions of Units with sub-percent active-editing rates, plus a small but high-frequency web novel subset (1000+ edits/year each).

## 5. Editorial Aggregate (Snapshot-Based)

### 5.1 Coverage

The editorial sub-aggregate of a Unit contains everything that is user-editable metadata, **excluding** BookIndex and engagement:

- `Unit` core fields: `status`, `visibility`, `nsfw`, `extra`, `slug`, `defaultLanguage`, `isLanguageNeutral`.
- `UnitTranslation[]` — all languages.
- `UnitSupportLanguage[]`.
- Type-extension table for this Unit (`Book`, `Game`, `Media`, `Post`, `Shelf`, `Realm`, `Link`, `Entity`, `Zone`).
- `Attribution[]` — who is credited (author, publisher, translator, etc.).
- `UnitTag[]` — membership only (tag presence/absence), **not** `score` or `voteCount`.

Explicitly excluded:

- `BookIndex` (handled by its own aggregate).
- `Post` targeting this Unit (comments are other Units, not part of this one's history).
- `ShelfItem` including this Unit (another user's shelf, not this Unit's state).
- `ReactionSummary`, score aggregates (engagement, not editorial).
- `RealmUnit` (membership, not editorial — may move to membership events later).

### 5.2 Strategy

Every user-initiated mutation of editorial state produces a new `UnitRevision`, with the full structural snapshot stored exactly once in `RevisionContent` keyed by SHA256 hash of the canonical payload. Identical content from different edits (e.g., a revert that restores an earlier state) does not duplicate content storage.

Payload structure:

```json
{
  "structural": {
    "unit": { "status": "PUBLISHED", "visibility": "PUBLIC", "...": "..." },
    "translations": [
      { "language": "zh", "title": "...", "description": "...", "...": "..." },
      { "language": "en", "title": "...", "...": "..." }
    ],
    "supportLanguages": [{ "language": "zh", "isPrimary": true, "sortOrder": 0 }],
    "extension": { "book": { "isbn13": "...", "pageCount": 300, "...": "..." } },
    "attributions": [
      { "entityId": "uuid-A", "role": "AUTHOR", "sortOrder": 0 }
    ],
    "tags": ["uuid-T1", "uuid-T2"]
  }
}
```

References (`entityId`, tag UUIDs) are stored as **IDs only**. There is no denormalized display cache. Rendering history resolves these IDs through the main server's batch-resolve API at display time.

### 5.3 Schema (Prisma)

```prisma
model UnitRevision {
  id          String   @id @default(dbgenerated("uuidv7()")) @db.Uuid
  unitId      String   @db.Uuid             // soft reference, not FK
  revision    Int                            // monotonic per unitId
  contentHash String   @db.VarChar(64)       // SHA256 of canonical payload
  userId      String   @db.Uuid              // every actor is a user
  message     String?                        // optional edit message
  createdAt   DateTime @default(now())

  content RevisionContent @relation(fields: [contentHash], references: [hash])

  @@unique([unitId, revision])
  @@index([unitId, createdAt(sort: Desc)])
  @@index([userId, createdAt])
  @@index([contentHash])
}

model RevisionContent {
  hash      String   @id @db.VarChar(64)
  payload   Json
  createdAt DateTime @default(now())

  revisions UnitRevision[]
}

model UnitAuditLog {
  id         String   @id @default(dbgenerated("uuidv7()")) @db.Uuid
  unitId     String   @db.Uuid
  snapshotId String?  @db.Uuid             // points to UnitRevision.id; NULL after snapshot deletion
  userId     String   @db.Uuid
  action     String   @db.VarChar(64)      // e.g. "TRANSLATION_UPDATE", "ATTRIBUTION_ADD"
  createdAt  DateTime @default(now())

  @@index([unitId, createdAt(sort: Desc)])
  @@index([userId, createdAt])
  @@index([snapshotId])
}
```

### 5.4 Revert Strategy — Frontend Reload + Normal Save

There is **no `revert` API**. The mechanism:

1. Moderator opens Unit's history timeline.
2. Selects a prior `UnitRevision`, clicks "Load this version into editor."
3. Frontend calls `GET /unit/:id/revisions/:revId`, populates the edit form with the returned payload.
4. Moderator may modify further or save as-is.
5. Save goes through the normal mutation path, producing a new `UnitRevision`.
6. Content-hash dedup: if the result exactly matches the loaded revision, no new `RevisionContent` is stored — only a new `UnitRevision` row pointing to the same hash.

UI can optionally derive "this edit matches state from revision N" by comparing content hashes; this is a display enhancement, not a data-model concept.

### 5.5 Deletion Strategy

Three deletion levels, with strong preference for the least destructive:

**Level A — Snapshot pointer deletion (admin tool):**
- `DELETE FROM UnitRevision WHERE id = ?`
- `UnitAuditLog.snapshotId` entries pointing to it are set to `NULL` (via `ON DELETE SET NULL` or application-level cascade).
- Audit log entries themselves remain — "someone did something at time T" is still recorded; the content is just no longer reachable.
- `RevisionContent` entries orphaned by this (no remaining `UnitRevision` references their hash) are removed by a periodic GC job.
- Fully reversible if the content blob is still GC-pending.

**Level B — Content deletion (compliance path, not day-to-day):**
- `DELETE FROM RevisionContent WHERE hash = ?`
- All `UnitRevision` rows pointing to that hash become dangling references.
- UI renders affected timeline entries using the `GONE` fallback (see §9.3).
- Purpose: GDPR erasure, illegal content removal.
- Requires elevated permission and logged justification.

**Level C — Not applicable** (editorial uses snapshot content; the "tombstone" concept is reserved for BookIndex events, see §6.6).

### 5.6 Bot writes

Bots are users. Their edits produce `UnitRevision` entries and `UnitAuditLog` entries identically to any other user. Content-hash dedup naturally eliminates "bot re-wrote the same data" cases — no new `RevisionContent` storage if the payload matches an existing hash.

UI may choose to filter or collapse bot-authored revisions in the timeline display (product decision, not data-model concern).

## 6. BookIndex Aggregate (Event-Sourced)

### 6.1 Conceptual model

`BookIndex` is attached 1:1 to `Book` via `bookUnitId`. It is **not** promoted to its own `Unit`. Rationale: the platform's i18n model is release-based — each language version is its own release Unit with its own `Book` and thus its own `BookIndex`. Layering `UnitTranslation` onto `BookIndex` would duplicate this mechanism.

An index is a **forest** of nodes:

```typescript
type IndexNode = {
  kind: 'GROUP' | 'ITEM'              // GROUP = volume/arc/part; ITEM = chapter entry
  title: string                        // required
  order?: number                       // optional display ordinal (e.g. "第四十八章" numbering)
  meta?: Record<string, unknown>       // extension fields
  chapterUnitId?: string               // optional; present only when a Chapter Unit exists
  children?: IndexNode[]               // only for GROUP kind
}

type IndexForest = IndexNode[]         // root is always a forest
```

Critical observation: **most `ITEM` nodes have no `chapterUnitId`.** A `CHAPTER` Unit is only created on demand:

- When a user wants to post a comment on that chapter.
- When the platform holds licensed content and stores the chapter's full body.

Otherwise, the chapter exists only as inline metadata (title + optional ordering/meta) within the BookIndex. Therefore history events must inline chapter data, not rely on Unit references.

### 6.2 Event operations

```typescript
type BookIndexOp =
  | { op: 'ADD_NODE';      path: number[]; node: IndexNode }
  | { op: 'REMOVE_NODE';   path: number[] }
  | { op: 'MOVE_NODE';     from: number[]; to: number[] }
  | { op: 'UPDATE_NODE';   path: number[]; changes: Partial<IndexNode> }
  | { op: 'BULK_REPLACE';  structure: IndexForest; reason: string }
  | { op: 'LINK_UNIT';     path: number[]; chapterUnitId: string }
```

`path` is a tuple of array indices into the forest: `[]` means root, `[2]` means the 3rd root node, `[0, 1]` means the 2nd child of the 1st root node.

`LINK_UNIT` is emitted when a Chapter Unit is first created for a node that previously had none (typically triggered by a user initiating the first comment on that chapter). It is distinct from `UPDATE_NODE` so the UI can render it differently (and optionally hide it from editorial timeline views).

**Note:** There is no `REVERT` operation. Rollback emits ordinary `ADD`/`REMOVE`/`MOVE`/`UPDATE` events in a batch (see §6.7).

### 6.3 Schema (Prisma)

```prisma
model BookIndexEvent {
  id         String   @id @default(dbgenerated("uuidv7()")) @db.Uuid
  bookUnitId String   @db.Uuid            // soft reference
  sequence   BigInt                        // strictly monotonic per bookUnitId
  op         String   @db.VarChar(32)
  payload    Json
  userId     String   @db.Uuid
  sessionId  String?  @db.Uuid             // groups events written together
  createdAt  DateTime @default(now())

  @@unique([bookUnitId, sequence])
  @@index([bookUnitId, sequence(sort: Desc)])
  @@index([userId, createdAt])
  @@index([sessionId])
}

model BookIndexSnapshot {
  id          String   @id @default(dbgenerated("uuidv7()")) @db.Uuid
  bookUnitId  String   @db.Uuid
  sequenceAt  BigInt                       // sequence number this snapshot reflects
  contentHash String   @db.VarChar(64)
  reason      String   @db.VarChar(32)     // "SCHEDULED" | "MANUAL" | "PRE_ROLLBACK"
  createdAt   DateTime @default(now())

  content BookIndexSnapshotContent @relation(fields: [contentHash], references: [hash])

  @@unique([bookUnitId, sequenceAt])
  @@index([bookUnitId, createdAt(sort: Desc)])
}

model BookIndexSnapshotContent {
  hash      String   @id @db.VarChar(64)
  structure Json                            // full IndexForest payload
  createdAt DateTime @default(now())

  snapshots BookIndexSnapshot[]
}

model BookIndexSequenceCounter {
  bookUnitId String @id @db.Uuid
  nextSeq    BigInt @default(1)
}
```

### 6.4 Sequence Generation

Per-`bookUnitId` strictly monotonic sequences are required for deterministic replay. Generation uses a dedicated counter table with atomic `UPDATE ... RETURNING`:

```sql
UPDATE "BookIndexSequenceCounter"
SET "nextSeq" = "nextSeq" + 1
WHERE "bookUnitId" = $1
RETURNING "nextSeq" - 1 AS seq;
```

The counter row is created at the same moment the first `BookIndexEvent` is written for a given `bookUnitId` (e.g., seed import).

Postgres row locking serializes concurrent writes on the same counter, which matches the semantics required — events within one `bookUnitId` are sequential, different books run in parallel.

### 6.5 Snapshot Triggering

A snapshot is created when any of these conditions is met:

1. **Event count threshold** — ≥ N events have been appended since the last snapshot (default **N = 100**).
2. **Time threshold** — ≥ T time has elapsed since the last snapshot and there has been at least one event (default **T = 30 days**).
3. **Forced on heavyweight ops** — immediately after a `BULK_REPLACE` or rollback batch, a snapshot is taken regardless of thresholds.

A daily scheduled job scans `BookIndexSequenceCounter` and `BookIndexSnapshot` to identify books whose counts/times have crossed thresholds and creates snapshots.

Dormant books (no events) produce no snapshots and occupy zero history storage.

### 6.6 State Reconstruction

Given a target sequence `N` for `bookUnitId`:

```
1. Find the latest BookIndexSnapshot with sequenceAt <= N:
      SELECT structure, sequenceAt
      FROM BookIndexSnapshot
      JOIN BookIndexSnapshotContent ON hash = contentHash
      WHERE bookUnitId = ? AND sequenceAt <= ?
      ORDER BY sequenceAt DESC LIMIT 1

2. Fetch events between the snapshot and the target:
      SELECT * FROM BookIndexEvent
      WHERE bookUnitId = ?
        AND sequence > snapshot.sequenceAt
        AND sequence <= N
      ORDER BY sequence ASC

3. Fold events onto the snapshot structure:
      state = events.reduce((s, e) => applyOp(s, e), snapshot.structure)
```

Typical case: snapshot within 100 events of target ⇒ 100 × ~270 bytes = 27 KB to process. Reconstruction is essentially instant.

The "current" state stored as `BookIndex.index` in the main DB is always the head state; it is updated in the same transaction as the event append.

### 6.7 Revert Strategy — Rollback Only

BookIndex supports exactly one revert semantic: **rollback to a prior sequence**. All other "undo" use cases must be performed as normal edits.

Rationale:

- Rollback corresponds to "this whole area is garbage, restore to point N." It is the nuclear option.
- For anything finer — fixing a single bad edit, restoring three deleted chapters, adjusting a moved section — the moderator uses the normal BookIndex editor to emit targeted `ADD`/`REMOVE`/`MOVE`/`UPDATE` events. The normal edit path is the surgical tool.
- This eliminates the need for a "surgical revert" algorithm (parallel replay, merge-against-later-edits), which has genuinely ambiguous semantics and significant implementation complexity.

Rollback mechanism:

```
1. Moderator picks a target sequence N in the timeline UI.
2. Backend:
   a) Reconstruct state_target (state at sequence N - 1, excluding event N onward).
   b) Reconstruct state_current (head state).
   c) Compute tree diff: state_current → state_target.
      Algorithm: path/title/chapterUnitId matching, unmatched before ⇒ REMOVE_NODE,
                 unmatched after ⇒ ADD_NODE, matched but moved ⇒ MOVE_NODE,
                 matched but changed ⇒ UPDATE_NODE.
      (Simple matching; not minimum tree edit distance. Correctness over optimality.)
   d) Generate a fresh sessionId.
   e) Write all diff events in a single transaction, all sharing that sessionId,
      all with userId = moderator.
   f) The first event's payload may carry a `rollbackTargetSequence: N` hint so
      the UI can label this sessionId's group as "rolled back to sequence N".
   g) Take a forced snapshot (reason = "PRE_ROLLBACK" or "POST_ROLLBACK" per
      product choice) to pin the new state.
3. Audit: no separate audit table. Rollback is visible as a sessionId group in
   the regular event stream.
```

Rollback discards edits that happened after sequence N (they still exist as events in history, but the current state no longer reflects them). Moderators must therefore use rollback deliberately — for the common "small vandalism with some good edits mixed in" case, normal editing is the right tool.

### 6.8 Small-Correction Pattern

The design intentionally makes moderator-initiated fixes indistinguishable from user edits at the storage layer:

| Problem | Mechanism |
|---|---|
| 1 chapter title is wrong | Moderator opens editor → `UPDATE_NODE` |
| 3 chapters deleted by vandal | Moderator opens editor → 3 × `ADD_NODE` |
| 10 chapters moved incorrectly | Moderator opens editor → `MOVE_NODE` × N |
| 100 chapters wiped | Rollback to pre-wipe sequence |
| Ongoing bot attack | Rollback + ban the bot's user |

The editor and its event emission are the surgical instrument. Rollback is the sledgehammer for wide-area damage.

### 6.9 Event Immutability

`BookIndexEvent` rows are append-only. **Events are never deleted.** Reasons:

- The event chain is the ground truth for state reconstruction at any point.
- Removing a row creates a sequence gap; later replays that happen to depend on that event's effect would be wrong.
- Immutability is the defining property of event sourcing.

Consequences:

- Vandalism is corrected by further edits, not by erasing the bad events.
- The history of who did what remains auditable permanently.
- Compliance exceptions are handled via narrow-scope mechanisms (see §8).

## 7. Cross-Cutting Concerns

### 7.1 Unified Actor Model

There is one column, `userId`, of type `String @db.Uuid`, on:

- `UnitRevision.userId`
- `UnitAuditLog.userId`
- `BookIndexEvent.userId`

No `actor` JSON, no `kind` enum, no separate bot/system types. Bots (crawlers, sync processes) have their own `User` records; the `dispatch` crawler service operates under a registered bot user. System-level operations that need to be attributed (e.g., `LINK_UNIT` triggered by comment creation) are attributed to the user whose action triggered them — with the `op` code differentiating visual treatment in the UI.

Permission, rate limiting, and moderation tooling are uniform. Banning a misbehaving bot is the same as banning any user.

### 7.2 Session Grouping

`BookIndexEvent.sessionId String?` is a UUID shared by all events written in the same logical operation batch. Use cases:

1. **Rollback batches** — all diff events generated by a rollback share one sessionId. Timeline UI collapses them into "rolled back to sequence N (expand 37 operations)."
2. **Bot sync runs** — a crawler adding N chapters in one sync pass uses one sessionId.
3. **Multi-change user edits** — a user making multiple changes in a single save shares sessionId across those events.
4. **Seed import** — initial BULK_REPLACE events (if used) can be grouped per import run.

`sessionId` is nullable for single-event operations. It is not consulted for replay correctness — only for UI grouping.

### 7.3 Reference Resolution & Fallback Contract

All inter-Unit references in history payloads are stored as **IDs only**. At display time, referenced entity display data is resolved via a batch API on the main server.

**Contract** (defined in `@rezics/contract`):

```typescript
export const UnitRefResolution = t.Union([
  t.Object({
    status: t.Literal('OK'),
    id: t.String(),
    type: t.String(),
    slug: t.String(),
    name: t.String(),
    avatar: t.Optional(t.String()),
    // ... other display fields
  }),
  t.Object({
    status: t.Literal('DELETED'),       // soft-deleted; last-known display preserved
    id: t.String(),
    lastKnownName: t.String(),
    deletedAt: t.String(),
  }),
  t.Object({
    status: t.Literal('GONE'),          // hard-deleted or 404
    id: t.String(),
  }),
  t.Object({
    status: t.Literal('RESTRICTED'),    // viewer lacks permission
    id: t.String(),
  }),
])

export const unitRefFallbackLabel = {
  DELETED: '(deleted)',
  GONE: '(removed)',
  RESTRICTED: '(private)',
} as const
```

The fallback labels and status shape are the single source of truth consumed by all clients (app, admin, future mobile, future wiki UI). UI renders history timelines using `status` to select rendering mode; `name` in `OK` and `DELETED` provides the visible label.

### 7.4 Batch Resolve Pattern

The main server exposes a public `POST /unit/resolve` endpoint:

```
Request:  { ids: string[] }
Response: UnitRefResolution[]
```

Characteristics:

- Public API (not `/internal`) — available to any authenticated client.
- Used by all surfaces: history timeline, quote rendering, mentions, rich link previews, search results.
- Frontend calls it directly from the component that consumes history data.
- Responses cached by TanStack Query using `queryKey: ['unit', id]`. Same entity referenced across many revisions is fetched once and served from cache.
- History service does **not** call this API or maintain its own resolution cache. Separation of concerns: history stores structural facts; main server owns current display truth.

### 7.5 Universal "View History" Link

Every Unit card, detail page, and relevant surface in the UI includes a "View history" link **regardless of whether that Unit has any history yet**.

- Clicking routes to the Unit's history page.
- If the Unit has no history records, the page renders an empty state: `"No history available yet."` with a tooltip explaining that history accumulates from collaborative editing.
- UI has no conditional to check "does this Unit have history?" before rendering the link — the link is unconditional.

Rationale: when new Unit types later gain history support, the UI requires no changes. This is a one-time UX commitment that scales.

## 8. Compliance & Special Cases

Event immutability is absolute in ordinary operation, but two compliance paths must exist as narrow exceptions.

### 8.1 User Anonymization (GDPR Right to Erasure)

When a user invokes the right to erasure:

```sql
UPDATE "BookIndexEvent"
SET "userId" = '00000000-0000-0000-0000-deleted00000'
WHERE "userId" = <target>;

UPDATE "UnitRevision"
SET "userId" = '00000000-0000-0000-0000-deleted00000'
WHERE "userId" = <target>;

UPDATE "UnitAuditLog"
SET "userId" = '00000000-0000-0000-0000-deleted00000'
WHERE "userId" = <target>;
```

- Event/revision rows are preserved; only the user reference is replaced with a reserved sentinel user.
- Replay is unaffected (no payload changes).
- Chain integrity is preserved.
- This does **not** count as "deleting events." It only removes PII.

### 8.2 Payload Scrub (Deferred — Design Position Only)

Rare cases — illegal content in a chapter title, PII in a payload — require actual modification of event or snapshot content:

- **For editorial** (snapshot): delete the `RevisionContent` row (Level B deletion). All `UnitRevision` rows pointing to that hash render via `GONE` fallback.
- **For BookIndex events**: a narrow-scope payload scrub replaces specific text fields (e.g., `title`, `meta`) with placeholder values. The event row is kept, `op`, `path`, `sequence`, and `userId` remain unchanged. Replay continues to work; the scrubbed content simply renders as "(removed)."

**This is explicitly deferred from v1.** The schema does not require changes to support it later. The design commits only to:

- Scrub is a compliance workflow with elevated permissions and audit logging, not an ordinary admin function.
- When built, it will replace specific string fields in event payloads, not delete rows.
- A scrub audit log (separate from the general audit log) will track each scrub operation.

This design position is recorded now so that the system is known-compatible with future compliance requirements without architectural change.

## 9. Transport & Deployment

### 9.1 In-Process Package (Initial)

`@rezics/history` is an in-process Bun package. The main server imports it and calls its functions within the same Prisma transaction as the business mutation:

```typescript
await prisma.$transaction(async (tx) => {
  // 1. Business mutation
  await tx.attribution.update({ ... })

  // 2. Assemble editorial aggregate snapshot from current tx view
  const payload = await buildEditorialAggregate(tx, unitId)

  // 3. Write revision via history package (same transaction)
  await history.editorial.recordRevision(tx, {
    unitId,
    payload,
    userId,
    action: 'ATTRIBUTION_UPDATE',
  })
})
```

For BookIndex:

```typescript
await prisma.$transaction(async (tx) => {
  // 1. Read current state, apply op locally, write head
  const current = await tx.bookIndex.findUniqueOrThrow({ where: { bookUnitId } })
  const next = applyOp(current.index, op)
  await tx.bookIndex.update({ where: { bookUnitId }, data: { index: next } })

  // 2. Append event via history package
  await history.bookIndex.recordEvent(tx, {
    bookUnitId,
    op,
    payload,
    userId,
    sessionId,
  })
})
```

Benefits of in-process:

- Strong transactional consistency: either the business write and history write both succeed or both roll back.
- No event-loss scenarios.
- No additional infrastructure.
- Simple operation.

### 9.2 Future Path: Outbox + LISTEN/NOTIFY

When history needs to be decoupled into a separate process (e.g., to protect write-path latency, to support multiple independent consumers, to enable replay), the transition path is already decided:

- Main server writes to an `Outbox` table in the same transaction as its business mutation.
- `NOTIFY outbox_channel` wakes worker(s).
- Workers (`LISTEN outbox_channel` + fallback polling) consume events in order and invoke the relevant processing — history, search, analytics, etc.
- Each worker tracks its consumption cursor (`OutboxConsumerCursor` table).

**Full CDC (Debezium + Kafka) is explicitly rejected** as over-engineered for current and foreseeable scale.

The in-process package is structured so that the transition to outbox requires only wrapping `recordRevision` and `recordEvent` with an outbox insert — no API shape changes for callers.

Meilisearch integration, which currently uses direct coupling, is **not** migrated to outbox as part of this plan. Migration can follow later once outbox is in use for history.

## 12. Decision Log

Key decisions and why they were made, for future readers of this document.

### Snapshot-based editorial, event-sourced BookIndex

Considered: uniform snapshot-per-edit for all aggregates; uniform event sourcing; hybrid. Chose hybrid because editorial and BookIndex have fundamentally different edit rhythms and the storage math is very different at scale (editorial ~100 edits/year per active Unit; BookIndex 1000+ per active web novel). One strategy cannot efficiently serve both.

### ID-only references, no denormalized display cache

Considered: denormalizing display data into snapshots so history is self-rendering. Rejected because:
- Temporal coupling — author renames would falsely appear in every book's history.
- Denormalization hell — unclear which fields to copy; schema drift.
- GDPR cost — PII scattered across every snapshot referencing a user.
- Storage inflation.

ID-only lets each Unit own its own history and each entity own its own identity over time.

### No surgical revert

Considered: Git-style cherry-pick revert that preserves edits after the reverted one. Rejected because:
- Ambiguous semantics with concurrent edits.
- Algorithm complexity (parallel replay + merge).
- "Fixing specific bad things" is better handled as new edits — the editor is the surgical tool.

Rollback is a sledgehammer; normal editing is the scalpel. Two orthogonal tools, no overlap.

### Unified user (bot = user)

Considered: an `actor` JSON/enum with kind=HUMAN|BOT|SYSTEM. Rejected in favor of a single `userId` column because:
- Schema uniformity.
- Permissions, rate limiting, moderation work uniformly.
- UI shows bots with their own avatar/name, just like any user.
- No special-case code paths.

Bots are users with elevated quotas or capabilities per the permission system, not a separate concept.

### In-process package, deferred outbox

Considered: build outbox + workers up front for future flexibility. Rejected in favor of in-process-first because:
- Strong transactional consistency is easier to reason about.
- Zero operational overhead initially.
- Future transition is bounded — just wrap with outbox insert.

### BookIndex as attached table, not a Unit

Considered: promoting BookIndex to its own Unit type with `UnitTranslation`. Rejected because:
- Platform i18n is release-based; each language release has its own Book + BookIndex already.
- Layering `UnitTranslation` on top would duplicate the release mechanism.
- Attached-table shape is simpler and aligned with existing conventions.

### Tree diff for rollback (simplified, not minimum edit distance)

Considered: Zhang-Shasha tree edit distance. Rejected in favor of simple path/ID matching. Minimum edit distance is not required — correctness and readability matter more than compactness. A rollback writing a few extra events is harmless.

### Audit log is pointer-only

Considered: audit log storing before/after values (Shape B from discussion). Rejected because it duplicates content already in revisions and introduces diff-storage complexity. Audit log stores `unitId`, `snapshotId?`, `userId`, `action`, `createdAt` — enough to answer "who did what when" without duplicating content.

### Content-hash dedup

SHA256 over canonical payload keys `RevisionContent` and `BookIndexSnapshotContent`. Identical content from multiple revisions/snapshots references the same row. Makes revert-via-reload free. Enables orphan-based GC.

### `sessionId` as universal grouping mechanism

Not a rollback-specific marker. Used for any operation batch: rollback, bot sync, multi-change user edits, bulk import. UI groups by `sessionId` uniformly. Extensible without schema change.

## 13. Glossary

- **Aggregate** — A cluster of related data treated as a consistency boundary (e.g., editorial fields of a Unit).
- **Editorial aggregate** — The wiki-editable metadata subset of a Unit: translations, attribution, tags, type-extension fields, core fields.
- **Event sourcing** — Representing state as a sequence of immutable change events; current state is derived by replaying events.
- **Rollback** — Rewriting current state to match a prior reconstructed state by emitting a batch of diff events.
- **Revision** — A snapshot row in editorial history, pointing to content by hash.
- **sessionId** — UUID shared by events written in the same logical batch, enabling UI grouping.
- **Tombstone** — A deferred compliance concept: event payload scrubbed while row and sequence are preserved.
- **Content-addressed storage** — Storage keyed by hash of content, automatically deduplicating identical payloads.
