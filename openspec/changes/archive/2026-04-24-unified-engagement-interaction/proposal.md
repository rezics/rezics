## Why

Engagement interactions (vote, reply, share, add-to-shelf) are fragmented across four parallel implementations — `ReactionBar`, `MiniActionBar`, `PostReactionFooter`, `ReactionStatistics` — none of which cover the full surface, and each content type (review, remark, excerpt, shelf card, post thread, post reply row) has its own partial wiring. There is no thread-aware reply composer, no threading line / collapse UI, and `ShelfPage` does not render the comment posts that already target it. This proposal unifies the interaction footer, adopts a Reddit-style visual language (arrow vote pill + icon-with-label actions, indent lines with expand/collapse), and refactors the reply-composition flow so every content type gets the same interaction across list, detail, and thread surfaces.

## What Changes

- **BREAKING** Introduce `ReactionBar` as the single interaction footer for every content type. Replace and remove `MiniActionBar`, `PostReactionFooter`, and `ReactionStatistics` usages. `ReactionBar` accepts two orthogonal props: `size` (`sm` / `md` / `lg`) and `actions` (ordered array of action tokens).
- Implement a Reddit-style vote pill atom: up-arrow + score + down-arrow, number-only (no "upvote" / "downvote" labels). Other actions render icon + text label (`💬 Reply`, `↗ Share`, `📚 Shelf`, `⋯ More`).
- Establish a per-content-type default-actions policy. "Content-as-artifact" types (review, remark, excerpt, shelf card) promote `Shelf` to a visible action on list cards; "discussion-type" posts (thread root card, reply row) keep `Shelf` in the `⋯` overflow menu on cards but promote it to visible on the detail page. `Share` is always visible across all surfaces.
- Introduce `ShelfPickerModal` and `ShelfAction` button. `ShelfAction` opens the modal; modal lets the user multi-select one or more shelves via `useCollectMutation`. `FavoriteButton` and the `collection/` feature remain untouched in this proposal (out of scope — they represent a distinct one-click "favorite shelf" shortcut).
- Introduce `ShareAction` with a copy-link / Web Share API popover. Replace ad-hoc share handling inside the current `ReactionBar` implementation.
- **BREAKING** Refactor `InlinePostForm` into `ReplyComposer` with two start-state modes: `progressive` (single-line placeholder that expands to the full editor on focus; used only by the "reply to the focal post" composer at the top of every detail page) and `expanded` (renders the full editor immediately; used everywhere a user clicks a 💬 Reply button). On blur, a progressive composer collapses back to single-line only when its body is empty; if the user has typed content it stays expanded. Multiple `expanded` composers may coexist inside one thread, each governed by the same blur-retain rule.
- **BREAKING** Adopt Reddit-style thread UI in `PostReply` and `PostTreeSection`: a vertical threading line connects parent to children with an L-bend to each child row, a `[−]` / `[+]` toggle circle sits on the left of every row that owns children, and both the icon and the threading line itself are clickable (hover hit-box widened to ~12 px) to toggle collapse. Default-collapse behaviour for `depth >= 2` is retained from the current spec.
- Change "💬 Reply" semantics by surface:
  - On a **list card** (any content type): navigate to the content's detail page and auto-focus the top `ReplyComposer` (which unfolds its progressive state).
  - Inside a **thread**, on any row that is not the focal post: inline-expand a new `ReplyComposer` (mode `expanded`) as a child of that row, anchored on the current thread page — no navigation, no modal.
  - On the **focal post** of a detail page: focus / unfold the top progressive composer.
- Mount a `PostTreeSection` + top `ReplyComposer` (progressive) on `ShelfPage`, keyed on `shelf.unitId`, so shelf-targeted comment posts finally render.
- Update `post-presentation-architecture` and `review-remark-ux` specs to reference `engagement-reaction-bar` instead of the removed atoms. Remove requirements about `PostReactionFooter` and replace reaction-count requirements with "renders `ReactionBar` with the appropriate `size` and `actions`".
- Treat click-propagation as a standard at the card level: the outer card wrapper owns a single `onClick` that navigates to the detail page; interactive leaf regions (`ReactionBar`, author header, avatar, inline links) must call `event.stopPropagation()`. This formalises the contract so future additions (e.g. clickable user avatars in `BookOwnerStrip`) follow the same rule.
- Reserve action tokens `funny` and `award` in the `ReactionBar` actions enum. No UI is shipped for them in this change; the reservation is purely schema-level so future changes can slot them in without re-keying.

## Capabilities

### New Capabilities
- `engagement-reaction-bar`: the unified `ReactionBar` component, its `size` / `actions` contract, its atom decomposition (`VoteGroup`, `ReplyAction`, `ShareAction`, `ShelfAction`, `OverflowMenu`), per-content-type default action sets (card vs. detail vs. thread-row), and the card-level click-propagation rule.
- `engagement-shelf-action`: the `ShelfAction` button and `ShelfPickerModal` UI, their wiring to `useCollectMutation`, and multi-shelf selection semantics.
- `engagement-share-action`: the `ShareAction` button, its popover (copy link + Web Share API fallback), and placement across surfaces.
- `post-reply-composer`: the `ReplyComposer` component, its two start-state modes (`progressive` vs `expanded`), blur-retain rules, multi-composer coexistence in a thread, and its use at every reply surface.
- `post-thread-ui`: the Reddit-style threading line, `[−]` / `[+]` collapse toggle, extended hover hit-box, and the concrete rule for where collapse state lives (already owned by `PostTreeSection` per existing spec — this adds the visual contract).
- `shelf-discussion`: mounting `PostTreeSection` and the progressive `ReplyComposer` on `ShelfPage`, keyed on `shelf.unitId`, with the same structure used on other detail pages.

### Modified Capabilities
- `post-presentation-architecture`: remove the "post body rendered via `PostReactionFooter`" requirement and the scattered reaction-count requirements; replace with "cards, reply rows, and detail focals render `<ReactionBar size=… actions=…/>` from `engagement-reaction-bar`". Adjust the thread-rendering requirement to name the new threading-line and collapse-toggle contract from `post-thread-ui`.
- `review-remark-ux`: rewrite the "Reaction counts on reviews and remarks" requirement to state that review and remark cards (and their detail pages) render `ReactionBar` with the content-as-artifact action set rather than owning bespoke count displays.

## Impact

- **Affected packages**: `package/app` (primary — all content features: `post/`, `review/`, `remark/`, `excerpt/`, `shelf/`, plus the `engagement/` folder itself), `package/ui` (may gain a shared threading-line / indent-rail primitive if one does not already exist), `package/api` (consumes the existing `useCollectMutation` — no change needed), `package/contract` (no change).
- **Affected files / call sites**: every `ReactionBar`, `MiniActionBar`, `PostReactionFooter`, `ReactionStatistics` import must be migrated. Every card (`PostCard`, `ReviewCard`, `RemarkCard`, `ExcerptCard`, `ShelfCard`), every detail component (`RemarkDetail`, `ReviewDetail`, `ExcerptDetail`), and `PostReply` will render `ReactionBar`. `InlinePostForm` call sites convert to `ReplyComposer`.
- **Out of scope**: `FavoriteButton` and the `collection/` feature are untouched. `funny` / `award` actions are reserved in enum only; no UI is delivered. `Share` integration with in-site direct messaging is out of scope; only copy-link + Web Share API ship.
- **Backward compatibility**: none required — all affected components are internal to `package/app`. The public Elysia API, the `@rezics/contract` schemas, and the persistence layer are unchanged. Reaction mutations (`useToggleReaction`), post-thread queries, and `useCollectMutation` are already in place and not modified.
- **Migration**: no data or schema migration. UI migration is mechanical — each card/detail site receives a `ReactionBar` with the action set prescribed by this change. `InlinePostForm` → `ReplyComposer` migration is a rename plus a prop change (`mode="progressive"` vs `mode="expanded"`).
- **Risk areas**: (1) event-propagation regressions when converting cards from nested clickable regions to a single outer `onClick` + `stopPropagation()` leaves — each migrated card should be spot-checked in Cosmos fixtures. (2) Cosmetic regressions in deeply nested threads when threading lines meet the depth cap — the visual cap rule from `post-presentation-architecture` must be preserved. (3) Shelf page performance if shelves accumulate large comment trees — the existing `PostTreeSection` pagination applies.
