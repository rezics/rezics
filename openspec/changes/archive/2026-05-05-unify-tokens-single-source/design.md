## Context

The rezics token system today is the residue of two prior partial migrations. Three artefacts coexist that should be one:

1. `package/ui/src/config/tokens/colors.ts` — TS export of `lightColors` / `darkColors`, intended as source-of-truth, **but no runtime code reads it**.
2. `package/ui/src/config/tokens.css` — ~660 lines of hand-written CSS variables under `.theme-rezics`, with three tiers (`--rezics-ref-*`, `--rezics-sys-*`, `--rezics-comp-*`) plus a parallel set of shadcn flat slots, plus 11 deprecated aliases. **This file is the de-facto runtime source.**
3. `package/ui/src/config/uno-config.ts` — UnoCSS theme that maps curated short className utilities (`text-primary`, `bg-surface-elevated`) to `var(--rezics-sys-color-*)` strings.

The `--rezics-sys-color-*` namespace exists for a single technical reason that has been verified by reading the `unocss-preset-shadcn@1.0.1` source code: that preset's `generateColorCSSVars` function silently drops any CSS variable name not in its hardcoded 32-entry `themeCSSVarKeys` list. To carry the rezics-specific tokens (surface ladder, brand-fill, sentiment, success/warning/error/info `*-fill`, `--container`, `--container-foreground`) we had to invent a parallel namespace.

Two subsequent investigations changed the picture:

**Finding A — `unocss-preset-shadcn` is dispensable.** Reading its dist source: ~96 lines of substance — 4 keyframes, 32 hardcoded CSS vars, a small `theme.colors` map wrapping each key in `oklch(var(--xxx))`. shadcn primitives consume className strings (`bg-primary`, `text-primary-foreground`); they have zero direct dependency on the preset itself. The preset can be replaced with 4 inline keyframe rules and a `theme.colors` mapping driven by the TS source.

**Finding B — UnoCSS preset-wind4 has a built-in theme→CSS-var generator (verified in `@unocss/preset-wind4@66.6.7` source).** When `theme.colors.primary = "#f4606c"` is declared, wind4:

- emits `:root, :host { --colors-primary: #f4606c; }` in its `theme` layer (on-demand: only USED tokens),
- resolves utility `bg-primary` to `color-mix(in srgb, var(--colors-primary) <alpha>, transparent)`,
- naming convention is `--<themeKey>-<nestedPath joined by ->`: `theme.colors.primary.foreground` → `--colors-primary-foreground`, `theme.radius.lg` → `--radius-lg`, `theme.font.sans` → `--font-sans`.

**Finding C — neither wind4 nor Tailwind v4 has built-in dark theme value-switching.** Confirmed via source code (`variants-BQhcPCjX.mjs:196-200`: `dark:` is a pure selector-prefix variant) and Tailwind v4 discussion #15083 (community is requesting this feature; Tailwind's recommended pattern is `:root { --x: light } .dark { --x: dark }` with `@theme inline` indirection). The community preset `unocss-preset-theme@0.14.1` exists but works by hijacking theme strings into double-layered `var()` indirection (`--un-preset-theme-colors-primary` → `--colors-primary`); pinned peerDep `@unocss/core@^0.63.4` does not match our `unocss@66.6.7`; hex literals get auto-split to RGB triplets; not validated with wind4.

The clean architecture follows: drop preset-shadcn, drop `tokens.css`, drop the `--rezics-*` namespace, drive everything from `tokens/colors.ts` via wind4's auto-emission, and write a 30-line preflight to emit `.dark { --colors-*: …; }` ourselves.

## Goals / Non-Goals

**Goals:**

- One source-of-truth file: `package/ui/src/config/tokens/colors.ts`. Every CSS variable, every UnoCSS theme entry, every Storybook color swatch derives from this file.
- Flat CSS variable namespace: `--colors-*`, `--radius-*`, `--motion-*`, `--font-*`, etc. — generated by wind4, not hand-written.
- shadcn primitives work unchanged. Their className utilities (`bg-primary`, `border-input`, `ring-ring`) resolve via `theme.colors.{primary,input,ring,…}` → `var(--colors-{primary,input,ring,…})`.
- Dark mode switches via `.dark` class on `<html>`. No hand-maintained CSS file; `darkColors` flows through a programmatic preflight.
- Extensions beyond shadcn's 32 vars (surface ladder, brand-fill, sentiment, semantic containers) are first-class citizens of `theme.colors`, with no parallel namespace.
- One-shot transition. No alias layer, no transitional flag.

**Non-Goals:**

- Changing what colors / radii / motion durations are used. The values from current `tokens.css` and `tokens/colors.ts` are preserved 1:1; only the names change.
- Designing a multi-theme system (compact, high-contrast, alternate brands). Single rezics light + dark, identical scope to today.
- Touching typography or spacing token shapes. Scope is the namespace + emission mechanism. Typography stays as-is in `tokens/typography.ts` and is consumed by Storybook MDX; its CSS variable names already happen to match wind4's convention or are not currently emitted.
- Renaming `package/ui/src/config/tokens/` or its subdirectory layout. Only the contents of `colors.ts` change.

## Decisions

### Decision 1: `tokens/colors.ts` is the single source of truth, NOT `tokens.css`

Two artefacts express the same data today; we keep the typed one, delete the other. `tokens/colors.ts` already has type definitions (`ColorTokens` interface), is reviewable in plain TS, and is amenable to programmatic transformation. `tokens.css` was hand-maintained and divergent in places.

**Alternative rejected — keep `tokens.css` as canonical, delete the TS:** TypeScript loses the ability to narrow color-mode types and forfeits compile-time guarantees. CSS-only authoring also makes it harder to derive Storybook swatches and run shape-validation tests.

**Alternative rejected — keep both as dual sources with a generator:** This is what got us into the current mess. Two sources always drift.

### Decision 2: Use UnoCSS preset-wind4's auto-emission for the light theme; write a small preflight for the dark override

Light values flow through wind4's standard channel: `theme.colors = lightColors` → wind4 emits `:root, :host { --colors-*: …; }` on-demand. Dark values flow through a `preflights[].getCSS` callback that flattens `darkColors` and emits `.dark { --colors-*: …; }`.

```ts
// approximate shape (final code lives in uno-config.ts)
function flattenColorVars(obj: unknown, parent = "colors", out: [string, string][] = []) {
  for (const [k, v] of Object.entries(obj as Record<string, unknown>)) {
    const path = `${parent}-${k}`;
    if (typeof v === "string") out.push([`--${path}`, v]);
    else if (v && typeof v === "object") flattenColorVars(v, path, out);
  }
  return out;
}

preflights: [
  {
    layer: "theme",
    getCSS: () => {
      const lines = flattenColorVars(darkColors).map(([k, v]) => `  ${k}: ${v};`).join("\n");
      return `.dark {\n${lines}\n}`;
    },
  },
]
```

**Alternative rejected — `unocss-preset-theme` for dark values:** Source-read finding C above. It rewrites every theme string to `var(--un-preset-theme-…)`, producing two layers of CSS variable indirection visible in DevTools, splits hex into RGB triplets (so `#f4606c` becomes `244 96 108` in the output), pins to `@unocss/core@^0.63.4` (we are on `66.6.7`), and is single-maintainer with no updates since 2024-10. The 30-line preflight is more controllable than this dependency.

**Alternative rejected — CSS `light-dark()` function:** Locks dark mode to `prefers-color-scheme` and disallows class-based override; we need class-based for the in-app theme toggle.

**Alternative rejected — `dark:` utility variants on every consumer (`bg-surface dark:bg-surface-dark`):** Doubles the className surface and forces every component to re-state its dark variant. Not a design-system mechanism.

### Decision 3: Drop `unocss-preset-shadcn`; absorb its substance into `uno-config.ts`

The 4 keyframe rules (`accordion-down/up`, `collapsible-down/up`) become inline `rules` entries. The 32 shadcn theme variables are not lost — they appear as keys in `theme.colors` (e.g. `theme.colors.primary`, `theme.colors.background`, `theme.colors.border`, `theme.colors.ring`, `theme.colors.chart-1..5`, `theme.colors.sidebar.*`). shadcn primitives never see the difference because they consume className strings, not raw `var()`.

The mapping from shadcn's 32 expected keys to rezics values is part of the new `tokens/colors.ts` shape:

| shadcn key | rezics source |
|---|---|
| `background` | `surface.canvas` |
| `foreground` | `text.primary` |
| `primary` | `brand.fill` |
| `primary-foreground` | `text.onBrand` |
| `secondary` | `surface.subtle` |
| `secondary-foreground` | `text.primary` |
| `muted` | `surface.sunken` |
| `muted-foreground` | `text.secondary` |
| `accent` | `surface.subtle` |
| `accent-foreground` | `text.primary` |
| `destructive` | `semantic.error.fill` |
| `destructive-foreground` | inverted, defined in tokens |
| `border` | `border.defined` |
| `input` | `border.defined` |
| `ring` | `border.focus` |
| `card` / `card-foreground` | `surface.elevated` / `text.primary` |
| `popover` / `popover-foreground` | `surface.elevated` / `text.primary` |
| `chart-1..5` | `chart.1..5` |
| `sidebar-*` | `sidebar.*` |

These are first-class entries in the unified `theme.colors`, NOT a separate "shadcn slot".

### Decision 4: rezics extensions live alongside shadcn keys in the same `theme.colors`

Extensions (everything beyond the 32 shadcn keys) appear as additional theme keys:

- `surface.elevated`, `surface.subtle`, `surface.sunken`, `surface.containerLowest..containerHighest`, `surface.tint`
- `text.secondary`, `text.tertiary`, `text.disabled`, `text.brand`
- `brand.fill`, `brand.fillHover`, `brand.fillActive`, `brand.textLight`, `brand.textDark`, `brand.container`, `brand.onContainer`
- `semantic.{success,warning,error,info}.{fill,textLight,textDark,container,onContainer}`
- `sentiment.{positive,negative}.{fill,textLight,textDark}`
- `border.{whisper,defined,strong,focus,error}`
- `inverse.{surface,onSurface,primary}`
- `chart.{1..5}`
- `sidebar.{background,foreground,primary,primaryForeground,accent,accentForeground,border,ring}`

These all generate flat CSS variables under wind4's convention (`--colors-surface-elevated`, `--colors-brand-fill`, …). No `--rezics-*` prefix; the rezics identity is in the brand value, not the prefix.

### Decision 5: Selector for dark mode is `.dark` (UnoCSS default), not `[data-theme="dark"]`

Today: `tokens.css` cascades under `.theme-rezics` and the design-system-foundation spec mentions `[data-theme="dark"]`. We adopt `.dark` because:

- It is wind4's default for `dark: 'class'`. No wind4 config needed.
- shadcn examples and ecosystem snippets all use `.dark`. Lower friction for any future shadcn primitive copy-in.
- Matches the user's prior note ("class-toggle mode"). Single class swap on `<html>`, no attribute selector overhead.

The theme toggle in the app changes `<html>`'s class between (no class) and `dark`.

### Decision 6: One-shot codemod, no transitional aliases

The codemod is a single run that rewrites `var(--rezics-*)` references and removes the parallel namespace. There is no alias layer (no `--rezics-color-primary: var(--colors-primary)` shim), no codemod followed by a deprecation period, no flag-gated rollout.

This change ships when the codemod completes successfully across all packages and `bun run check:convention` (with the updated R9) passes. If something is missed, that's a follow-up bug, not a rollout step.

### Decision 7: R9 (check-convention) is updated, not removed

R9 today bans `text-rezics-color-*` utilities, `var(--rezics-…-color-…)` inside className contexts, and 11 deprecated names. After this change:

- The "deprecated names" list is removed (the namespace is gone).
- The ban shifts to: any `var(--rezics-*)` reference anywhere in source files outside the codemod's known exception (there should be none after the migration; R9 guards against regression).
- The curated short-name expectation stays.

### Decision 8: `tokens/colors.ts` shape — flat, both modes, hex literals

Final shape (illustrative, not the literal final code):

```ts
export type ColorScheme = "light" | "dark";

// One unified shape. shadcn keys + rezics extensions, both modes.
export interface FlatColorTokens {
  // shadcn 32
  background: string;
  foreground: string;
  primary: string;
  "primary-foreground": string;
  // …
  // rezics extensions
  surface: { canvas: string; elevated: string; subtle: string; /* … */ };
  brand: { fill: string; fillHover: string; /* … */ };
  semantic: { success: { fill: string; container: string; /* … */ }; /* … */ };
  // …
}

export const lightColors: FlatColorTokens = { /* hex literals */ };
export const darkColors:  FlatColorTokens = { /* hex literals */ };
```

Hex over OKLCH — Decision continues from the earlier explore session: hex is reviewable in code review, recognized by every tool, and we have no programmatic-derivation use case that needs OKLCH.

`tokens/index.ts` continues to re-export from each token module unchanged.

### Decision 9: Storybook MDX and convention checks track the new namespace

Storybook stories that reference token names in display text are updated to show the flat names. The `check-tokens.ts` script's expected variable list is regenerated from `tokens/colors.ts`. R9 in `check-convention.ts` is updated.

## Risks / Trade-offs

**[Risk] Inline-style usage of `var(--rezics-sys-color-*)` in SVG fills, gradients, etc.** → Codemod handles these. The current `R9` exception for inline `style={{}}` is preserved but rewritten to flat names. We grep for `var\(--rezics-` across all extensions; the count today is 558, which is the size of the codemod's input.

**[Risk] Storybook MDX files reference long token names in prose.** → Codemod also covers `*.mdx` files. Inline code blocks that document the *old* names in spec history are kept (those are documentation of what changed, not active references).

**[Risk] preset-wind4's on-demand mode only emits used tokens.** If a token is referenced only via inline `var(--colors-foo)` and never via a className, wind4 will not emit it. → Mitigation: such inline references are added to UnoCSS `safelist` so the theme preflight sees them. Alternatively, switch the theme preflight `mode` to a non-"on-demand" value for the rezics-extension keys; investigate during implementation. The on-demand approach is preferred because it keeps generated CSS lean.

**[Risk] Color-mix wrapping interaction with shadcn primitives.** wind4 wraps theme colors in `color-mix(in srgb, var(--colors-x) <alpha>, transparent)`. Some shadcn snippets in the wild assume the variable is the raw color. → Mitigation: shadcn primitives in this repo are already integrated and consume className utilities, not raw vars. Verified via grep of `package/ui/src/shadcn/` — no raw `var(--*)` usage in component source files.

**[Risk] Selector change `[data-theme="dark"]` → `.dark` requires updating the theme-toggle code.** → The theme-toggle hook lives in `package/app` and is one place. The change is mechanical: replace `setAttribute('data-theme', mode)` with `classList.toggle('dark', mode === 'dark')`.

**[Risk] R9 false positives during the codemod transition (CI sees half-converted tree).** → Codemod runs locally before commit, the convention check runs as a single gate after the sweep is complete. There is no half-state in the merged history.

**[Risk] Some existing CSS file that I haven't grep-found uses `--rezics-*`.** → Pre-merge: rerun the count and inspect every file in the result list. Any file that doesn't fit the codemod pattern is migrated by hand and the codemod regex is widened.

## Migration Plan

1. Land all token-source changes in a single PR on `dev`.
2. Codemod runs locally as part of the PR. CI verifies it left no `--rezics-*` references.
3. `bun run check:convention` (with new R9) runs on the PR and gates merge.
4. After merge, a follow-up PR may delete `unocss-preset-shadcn` from `bun.lock` if not auto-resolved.

**Rollback:** revert the merge commit. The single-PR shape makes this clean. `tokens.css` and the rezics namespace come back together; codemod's rewrites are reversed by the revert.
