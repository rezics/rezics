## Context

Rezics already treats `Unit` as the global identity and lifecycle spine for
catalog records, posts, tags, media, and other content surfaces. `Unit.rating`
is a maintainer-declared content suitability label used by discovery filters and
user opt-ins. AI usage needs a separate disclosure surface because it describes
content provenance, not audience suitability.

Current external practice is converging around disclosure/provenance signals
rather than age-style grading. C2PA and IPTC focus on media provenance metadata,
while the IETF AI disclosure header draft uses coarse modes such as AI-modified,
AI-originated, and machine-generated. Rezics should adopt the coarse mode model
internally and leave room for richer provenance metadata later.

## Goals / Non-Goals

**Goals:**

- Add a Unit-level AI disclosure mode with stable shared identifiers.
- Keep `ContentRating` behavior, filtering, and user opt-ins unchanged.
- Make AI disclosure available through contracts, persistence, mapping, and
  relevant frontend metadata surfaces.
- Keep supporting details optional so old Units and uncertain imports can be
  represented without inventing false precision.
- Preserve compatibility for existing clients that ignore the new field.

**Non-Goals:**

- Do not implement cryptographic provenance verification such as full C2PA
  manifest validation.
- Do not classify AI disclosure as safety, quality, copyright, or age risk.
- Do not derive disclosure automatically from text/image detection heuristics.
- Do not require model/provider/reviewer details for every Unit.
- Do not use AI disclosure to hide or allow content by default.

## Decisions

### Store a coarse Unit-level disclosure mode

Add a canonical `AiDisclosureMode` enum with these values:

- `NONE`: the maintainer asserts no AI involvement in the Unit's declared
  public-facing content.
- `AI_ASSISTED`: human-authored content with AI assistance such as editing,
  translation, cleanup, summarization, or formatting.
- `AI_ORIGINATED`: AI generated the initial or substantial draft, followed by
  meaningful human editing or review.
- `MACHINE_GENERATED`: the content is primarily generated by AI with little or
  no human review.
- `UNKNOWN`: provenance is unknown or not asserted.

The default for existing and newly-created Units should be `UNKNOWN`, not
`NONE`. `NONE` is an affirmative provenance claim; `UNKNOWN` avoids claiming
that historical data is human-created.

Alternative considered: use a boolean `isAiGenerated`. This is too lossy for
assisted and reviewed workflows and encourages unclear UI copy.

Alternative considered: use a numeric level. This looks like a risk/quality
rating and would invite false ordering.

### Keep supporting metadata optional and secondary

The first implementation should allow optional details such as model, provider,
human review flag, source standard, and disclosure source. These details should
not be required for validation of the coarse mode.

Suggested shape:

```ts
type AiDisclosureDetails = {
  model?: string;
  provider?: string;
  reviewedByHuman?: boolean;
  disclosedBy?: "USER" | "MODERATOR" | "SYSTEM" | "IMPORT";
  sourceStandard?: "C2PA" | "IPTC" | "SELF_DECLARED" | "OTHER";
};
```

This can live in a JSON column or a typed `Unit.extra` subshape only if the
implementation has strong conventions for validating and mapping it. The coarse
mode should be a typed first-class field because it is likely to be queried,
indexed, displayed, and filtered.

Alternative considered: store everything in `Unit.extra`. That avoids a
migration, but makes query/index semantics and cross-package contracts weaker.

### Expose disclosure through existing Unit DTO boundaries

`package/contract` should define the enum/schema and add optional fields to
Unit-facing DTOs. Book, media, post/chapter, and content search DTOs should
receive the field only where they already mirror Unit metadata. App code should
consume contract types instead of duplicating literals.

### Display as disclosure, not moderation

Frontend UI should present the field as an AI disclosure/provenance badge or
metadata selector. It must not visually imply that AI content is automatically
adult, unsafe, low quality, or forbidden.

If filtering is added, it should be an explicit AI disclosure filter separate
from rating filters.

## Risks / Trade-offs

- Ambiguous claims -> Use `UNKNOWN` as the conservative default and reserve
  `NONE` for affirmative declarations.
- Overloaded semantics -> Keep naming centered on disclosure/provenance, not
  rating or risk.
- Search index drift -> Include the field in index documents only through the
  existing search sync/rebuild path and add tests for mapped documents.
- UI clutter -> Show compact badges in public surfaces and fuller controls only
  in metadata/edit screens.
- Future C2PA/IPTC support -> Keep optional details extensible and do not bake
  external metadata vocabulary into the primary enum.

## Migration Plan

1. Add the shared contract enum/schema and DTO fields.
2. Add the server persistence field and migration with default `UNKNOWN`.
3. Backfill existing rows to `UNKNOWN`.
4. Update mappers, create/update inputs, and tests for Unit and Book metadata
   flows.
5. Add search document mapping if search surfaces need badge/filter support.
6. Add frontend edit/display UI in existing Unit/Book metadata surfaces.
7. Roll back by ignoring the optional field in clients; database rollback only
   requires dropping the new field if no deployed code depends on it.

## Open Questions

- Should `AiDisclosureDetails` be stored as a dedicated `Unit.aiDisclosureExtra`
  JSON field or nested under existing `Unit.extra` with strict validation?
- Should public search filtering ship in the first implementation, or only
  indexing/display?
- Which Unit types should expose editable controls first: all Units, or only
  catalog/content types such as `BOOK`, `MEDIA`, `POST`, `IMAGE`, and `VIDEO`?
