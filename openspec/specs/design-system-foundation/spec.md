# design-system-foundation Specification

## Purpose

Defines the foundation tokens (color, typography, spacing, radius, elevation, motion) that govern the rezics visual identity across `@rezics/app`, `@rezics/admin`, `@rezics/editor`, `@rezics/folio`, and `@rezics/ui`. Tokens are authored as TypeScript constants under `package/ui/src/config/tokens/` and exposed at runtime via the flat UnoCSS-generated CSS custom-property cascade (`--colors-*`, `--radius-*`, `--motion-*`, `--font-*`, etc.). Light/dark mode switches via the `dark` class on `<html>`; there is no JavaScript-side theme provider.

## Requirements

### Requirement: CSS custom property namespace is flat (UnoCSS-derived)

All design-system CSS custom properties SHALL use the flat naming convention generated by UnoCSS preset-wind4 from the theme configuration: `--colors-<path>`, `--radius-<path>`, `--motion-<path>`, `--font-<path>`, etc. The `--rezics-*` prefix and the `--rzc-*` shorthand SHALL NOT be used. Font-family local fallback names continue to use `'rezics-sans'`, `'rezics-serif'`, `'rezics-mono'` (these are font-face identifiers, not CSS custom properties).

#### Scenario: No legacy prefix remains

- **WHEN** `rg "--rezics-|--rzc-" -g '!openspec/changes/**' -g '!openspec/specs/design-system-foundation/spec.md.bak'` is run from the repository root
- **THEN** there SHALL be zero matches in source files (`.ts`, `.tsx`, `.css`, `.mdx`, `.json`)

#### Scenario: Tokens emitted by UnoCSS theme preflight

- **WHEN** the UnoCSS-generated CSS is inspected
- **THEN** the `:root, :host` selector SHALL declare `--colors-*` (and `--radius-*`, `--font-*`, etc. as referenced by used utilities) emitted by preset-wind4 from `package/ui/src/config/uno-config.ts`'s `theme`
- **AND** there SHALL NOT be a hand-written `tokens.css` declaring these variables

#### Scenario: Dark mode override

- **WHEN** the `<html>` element carries class `dark`
- **THEN** the `.dark` selector emitted by `uno-config.ts`'s preflight SHALL override mode-sensitive tokens (`--colors-background`, `--colors-foreground`, `--colors-primary`, `--colors-surface-elevated`, `--colors-text-secondary`, etc.) to their dark-mode values
- **AND** `--colors-brand-fill` SHALL remain `#f4606c` in both modes (it is a fill, not text)

### Requirement: Brand color contrast policy

The brand color `#f4606c` (轮回红) SHALL be used as a UI fill (button background, badge fill, focus ring, icon fill, decorative accent) but SHALL NOT be used as a text color. Brand-colored text SHALL route through `--colors-text-brand` (`#C4433A` light / `#fa7882` dark), which is contrast-verified for AA-body on its corresponding canvas.

#### Scenario: Body text using brand fill is forbidden

- **WHEN** any UI surface renders body text (paragraph, label, caption sized < 18px regular and < 14px bold)
- **THEN** the text color SHALL NOT be `#f4606c` or `var(--colors-brand-fill)`
- **AND** any brand-colored body text SHALL use `var(--colors-text-brand)` or the `text-brand` className utility

#### Scenario: `text-brand` exists for both modes

- **WHEN** UnoCSS-generated CSS for the rezics theme is inspected
- **THEN** `:root, :host` SHALL declare `--colors-text-brand` with the light value `#C4433A`
- **AND** the `.dark` block SHALL override it to `#fa7882`

### Requirement: Semantic colors with fill / text-light / text-dark variants

The design system SHALL provide `success`, `warning`, `error`, and `info` semantic colors. Each semantic SHALL expose a `*-fill` token (3:1 UI contrast minimum) and `*-text` tokens contrast-verified for AA-body 4.5:1 against the canvas in each mode. Components SHALL select the variant matching the use case (fill for chips/icons/borders, text for body copy).

#### Scenario: Semantic fill tokens exist

- **WHEN** `--colors-success-fill`, `--colors-warning-fill`, `--colors-error-fill`, `--colors-info-fill` are referenced
- **THEN** all four SHALL resolve to declared values in both light and dark themes

#### Scenario: Semantic text tokens exist with AA-body contrast

- **WHEN** `--colors-success-text`, `--colors-warning-text`, `--colors-error-text`, `--colors-info-text` are referenced
- **THEN** all four SHALL resolve to declared values verified against `--colors-background` for AA 4.5:1 in their respective mode

### Requirement: Border-led depth, not shadow-led

Containment SHALL be expressed primarily via `--colors-border-whisper` (default surface boundary, 1px at 8% opacity), whitespace, and the shadcn Card surface API. Sections, table rows, navs, and generic panels SHALL NOT carry box-shadow. Cards SHALL use shadcn `<Card surface="plain" | "contained" | "elevated">`, SHALL use the small `rounded-md` card radius, and SHALL keep same-color/page-color fills rather than tonal card backgrounds. Only `surface="elevated"` MAY carry a soft `shadow-1`, and only for same-color/near-same-color media-rich recommendation or article cards. Heavier shadow tokens SHALL exist only for floating or modal-tier surfaces (dialogs, command palettes, context menus, popovers).

#### Scenario: Whisper border is the default boundary

- **WHEN** `--colors-border-whisper` is referenced
- **THEN** it SHALL resolve to `rgba(0,0,0,0.08)` in light mode and `rgba(255,255,255,0.10)` in dark mode

#### Scenario: Modal-tier shadow tokens exist

- **WHEN** `--shadow-1`, `--shadow-2`, `--shadow-3`, `--shadow-modal` are referenced
- **THEN** all four SHALL resolve to declared values
- **AND** `--rezics-shadow-modal` SHALL be a 4-layer accumulating stack

#### Scenario: Elevated card shadow is restricted

- **WHEN** an inline card needs soft visual separation
- **THEN** it SHALL use shadcn `<Card surface="elevated">`
- **AND** it SHALL NOT hand-roll `shadow-sm`, `shadow-md`, or custom `box-shadow` classes outside the Card surface API
- **AND** `shadow-2`, `shadow-3`, and `shadow-modal` SHALL remain reserved for floating or modal-tier surfaces

### Requirement: Typography uses Latin + CJK layered families

`font-sans`, `font-serif`, and `font-mono` SHALL each compose a Latin face (Inter / Source Serif 4 / CaskaydiaMono) and a CJK face (Source Han Sans / Source Han Serif / Sarasa Mono) via `unicode-range` segmentation. Default CJK region SHALL be Traditional Chinese (`zh-hant`); `:lang(zh-Hans|zh-CN)`, `:lang(ja)`, `:lang(ko)` SHALL switch the active CJK family via the `--font-sans-cjk` / `--font-serif-cjk` custom property.

#### Scenario: Font stack includes Latin and CJK in order

- **WHEN** `--font-sans` is resolved
- **THEN** the `font-family` value SHALL list `'Inter'` first, the local fallback `'rezics-sans'`, and a CJK family before any system fallback

#### Scenario: `:lang()` switches regional CJK

- **WHEN** content carries `lang="zh-hans"` or `lang="ja"` or `lang="ko"` on an ancestor element
- **THEN** the matching `:lang()` rule SHALL override `--font-sans-cjk` / `--font-serif-cjk` to the regional Source Han variant

### Requirement: Type scale is viewport-responsive via clamp()

The type scale SHALL define eight size tokens (`text-xs` through `text-3xl`), each authored as `clamp(min, preferred-with-vw, max)` so type scales smoothly with viewport width without manual breakpoints.

#### Scenario: All scale tokens use clamp()

- **WHEN** the typography token module is inspected
- **THEN** every size in `text-xs` / `text-sm` / `text-base` / `text-md` / `text-lg` / `text-xl` / `text-2xl` / `text-3xl` SHALL be a `clamp()` expression
- **AND** the min and max SHALL bracket sensible mobile / desktop sizes per the foundation brief

### Requirement: Line-height policy enforces minimum 1.30

The system SHALL provide `leading-reader` (1.60), `leading-body` (1.55), `leading-ui` (1.40), and `leading-dense` (1.30) tokens. Component code SHALL NOT set numeric `line-height` below `1.30`. Reader content (book content, > 3-paragraph long-form articles) SHALL use `leading-reader`.

#### Scenario: No component sets line-height below 1.30

- **WHEN** `rg "lineHeight: ['"]?1\\b|line-height: 1\\b"` is run across `package/ui/src/`, `package/app/src/`, `package/admin/src/`, `package/editor/src/`, `package/folio/src/`
- **THEN** matches SHALL be either fixed or document the exception inline

### Requirement: Motion respects `prefers-reduced-motion`

`layers.css` SHALL include a global `@media (prefers-reduced-motion: reduce)` rule that collapses `animation-duration` and `transition-duration` to `0ms` for all elements. Component animations SHALL therefore not need to handle the preference individually.

#### Scenario: Global reduced-motion rule exists

- **WHEN** `package/ui/src/shared/styles/layers.css` is parsed
- **THEN** there SHALL be a `@media (prefers-reduced-motion: reduce)` block applying `animation-duration: 0ms !important` and `transition-duration: 0ms !important` to `*`, `*::before`, `*::after`

### Requirement: Token TypeScript modules are the single source of truth

The rezics design system SHALL define all foundation tokens (color, typography, spacing, radius, elevation, motion) as TypeScript constants under `package/ui/src/config/tokens/`. Every other consumer — UnoCSS theme entries in `uno-config.ts`, runtime CSS variables emitted by UnoCSS, breakpoint constants in `package/ui/src/config/breakpoints.ts` — SHALL derive from these modules. There SHALL NOT be a parallel hand-written CSS file (`tokens.css`, `layers.css` token block, or equivalent) declaring the same variables. Token authors SHALL NOT introduce parallel sources of truth.

#### Scenario: All token categories live under the tokens directory

- **WHEN** the contents of `package/ui/src/config/tokens/` are listed
- **THEN** the directory SHALL contain `colors.ts`, `typography.ts`, `spacing.ts`, `radius.ts`, `elevation.ts`, `motion.ts`, and `index.ts`
- **AND** `index.ts` SHALL re-export from each of the six token modules

#### Scenario: UnoCSS config consumes tokens TS directly

- **WHEN** `package/ui/src/config/uno-config.ts` is inspected
- **THEN** its `theme.colors` SHALL be assigned from `lightColors` (or a transformation thereof) imported from `./tokens/colors`
- **AND** its `preflights[]` SHALL include an entry that emits `.dark { --colors-*: …; }` derived programmatically from `darkColors`
- **AND** there SHALL NOT be any hex-literal color value typed inline in `uno-config.ts`

#### Scenario: Hand-written `tokens.css` is forbidden

- **WHEN** `package/ui/src/config/` is listed
- **THEN** there SHALL NOT be a `tokens.css` file
- **AND** the runtime CSS variable namespace SHALL be entirely UnoCSS-emitted

### Requirement: Theme switches via `.dark` class

The light/dark theme SHALL switch via the `dark` class on the `<html>` element (matching UnoCSS preset-wind4's `dark: 'class'` default). The `.dark` preflight emitted by `uno-config.ts` SHALL deliver all mode-sensitive token values. There SHALL NOT be a JavaScript-side theme object, a React context provider, or a runtime theme-injection layer in the runtime path. Components SHALL receive token values exclusively through CSS custom properties.

#### Scenario: Mode switch updates DOM class

- **WHEN** the user (or an app-level theme toggle) switches to dark mode
- **THEN** the `<html>` element SHALL receive the class `dark`
- **AND** the `--colors-*` cascade emitted by the `.dark` preflight SHALL resolve to dark-mode values
- **AND** no React component remount SHALL be required for the change to take effect

#### Scenario: No JavaScript theme provider in runtime

- **WHEN** the running React tree of `@rezics/app` or `@rezics/admin` is inspected
- **THEN** there SHALL be no JavaScript-side theme provider injecting palette / spacing / typography values
- **AND** components SHALL receive token values exclusively through CSS custom properties

### Requirement: shadcn theme keys are first-class entries in `theme.colors`

The 32 shadcn theme variable names (`background`, `foreground`, `card`, `card-foreground`, `popover`, `popover-foreground`, `primary`, `primary-foreground`, `secondary`, `secondary-foreground`, `muted`, `muted-foreground`, `accent`, `accent-foreground`, `destructive`, `destructive-foreground`, `border`, `input`, `ring`, `chart-1` ... `chart-5`, `sidebar-background`, `sidebar-foreground`, `sidebar-primary`, `sidebar-primary-foreground`, `sidebar-accent`, `sidebar-accent-foreground`, `sidebar-border`, `sidebar-ring`) SHALL appear as keys (or nested key-paths) in `package/ui/src/config/uno-config.ts`'s `theme.colors`. There SHALL NOT be a parallel namespace for shadcn variables. shadcn primitives SHALL consume these tokens via UnoCSS-generated className utilities (`bg-primary`, `text-foreground`, `border-input`, `ring-ring`, etc.) — not via raw `var(--primary)` references in source files.

#### Scenario: shadcn primitive renders without preset-shadcn

- **WHEN** `unocss-preset-shadcn` is removed from the dependency tree
- **AND** a shadcn primitive (Button, Dialog, Tooltip, etc.) is rendered
- **THEN** it SHALL receive the same visual styling as before
- **AND** its background, foreground, border, and ring colors SHALL resolve from `theme.colors.{primary,foreground,input,ring,...}` via UnoCSS-emitted `--colors-*` variables

#### Scenario: No raw shadcn-prefixed var references in source

- **WHEN** `rg "var\(--(primary|background|foreground|card|popover|secondary|muted|accent|destructive|border|input|ring|chart-|sidebar-)"` is run across `package/{ui,app,admin,editor,folio}/src/`
- **THEN** there SHALL be zero matches outside generated CSS or vendor files (shadcn primitives consume className, not raw var)

### Requirement: rezics extension keys live alongside shadcn keys without prefix

Tokens beyond the shadcn 32 (the surface-container ladder, brand-fill / brand-textLight / brand-textDark, semantic `*-fill` / `*-container` / `*-onContainer`, sentiment positive / negative, brand text, surface tint, inverse roles) SHALL appear as additional keys in the same `theme.colors`. They SHALL NOT carry a `rezics-` segment in their path or generated CSS variable name. The rezics identity is in the values, not the variable names.

#### Scenario: Surface ladder accessible by short name

- **WHEN** a component uses `bg-surface-elevated` or `bg-surface-container-high`
- **THEN** UnoCSS SHALL resolve via `theme.colors.surface.elevated` to `var(--colors-surface-elevated)`
- **AND** `--colors-surface-elevated` SHALL be defined in `:root, :host` and overridden in `.dark`

#### Scenario: Brand-fill is distinct from `primary`

- **WHEN** `theme.colors` is inspected
- **THEN** both `primary` (shadcn slot, `#f4606c`) and `brand.fill` (rezics extension, identical value) SHALL exist as entries
- **AND** their generated CSS variables (`--colors-primary` and `--colors-brand-fill`) SHALL coexist without conflict
