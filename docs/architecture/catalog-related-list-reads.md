# Native related-list name labels

Software release results and Program episode occurrences attach one optional name label after the child identity has passed its owner's read policy. The label is an active, unscoped, spoiler-0 named form. It is a display fallback, not a declaration that the name is official or preferred in the viewer's language.

The UI requests 20 releases or 30 occurrences. The API accepts at most 100 children; repeated episode identities are deduplicated for label lookup. One batched lateral query applies active-state, spoiler-0 and null-scope predicates before ordering by name ID and limiting to one result per identity. These predicates exactly match the existing owner-local `*_named_form_preview_idx` partial index on `(owner_id, id)`. A large collection of withdrawn, scoped or spoiler names cannot displace the eligible public name or expand the candidate scan.

At 500 million eligible named forms, an illustrative 64-byte preview index entry is 32 GB; at 3 billion it is 192 GB, excluding PostgreSQL page overhead and replication. Named-form tables are currently unpartitioned. A future 64-way owner-ID partition cutover would average 7.8 million and 46.9 million entries per partition; that is placement math, not existing DDL. This query adds no new index or write amplification. Its work is at most 100 indexed owner-key lookups and 100 returned labels, with logarithmic index descent at both corpus sizes.

Assuming ordinary labels average 100 UTF-8 bytes, a 100-item result adds roughly 10 KB plus JSON overhead. The name contract permits 128 KiB, so the pathological pre-wire result is approximately 12.5 MiB. The native page serialization boundary applies its existing 2 MiB wire budget; this helper does not truncate or invent names. At 100 maximum-sized related-list requests per second, the budget is 10,000 point lookups and labels per second. This is a planning envelope, not a measured throughput claim. Keep API and database concurrency bounded; monitor response bytes, statement latency, read buffers and pool wait time. The target p95 is 250 ms for ordinary labels on a warm target; production qualification must measure representative visibility and alias skew at the provisioned concurrency.

No whole-corpus maintenance, offset pagination, recurring rebuild or in-process corpus cache is introduced. The query carries each owner identity explicitly, so a future owner-ID partition/shard router can route each bounded batch. Such a cutover needs its own concrete FK, migration and recovery qualification. The local HTTP fixture checks readable release and episode labels alongside permissions, revisions and pagination; it does not certify production throughput at 500 million or 3 billion rows.
