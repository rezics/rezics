# Native related-list name labels

Software release results and Program episode occurrences attach one optional name label after the child identity has passed its owner's read policy. The label is an active, unscoped, spoiler-0 named form. It is a display fallback, not a declaration that the name is official or preferred in the viewer's language.

The UI requests 20 releases or 30 occurrences. The API accepts at most 100 children; repeated episode identities are deduplicated for label lookup. One batched lateral query reads at most the first 50 active named forms per identity through the existing `(owner_id, id) WHERE state = 'active'` index, then selects the first eligible form. If those 50 contain no eligible name, the response contains `name: null`; the UI uses the occurrence number or release date before the localized unnamed fallback. It never scans an identity's entire alias set to improve a label.

At 500 million active named forms, an illustrative 64-byte active index entry is 32 GB; at 3 billion it is 192 GB, excluding PostgreSQL page overhead and replication. Named-form tables are currently unpartitioned. If operational thresholds require a partition cutover, 64 owner-ID hash partitions would average 7.8 million and 46.9 million entries; this is a future placement option, not existing DDL. The label path creates no rows or indexes and has no write amplification. Query work is bounded by 100 owner-key lookups plus at most 5,000 candidate rows at either cardinality. Owners with extreme alias skew are handled by the same 50-row candidate bound; hidden or scoped candidates may intentionally yield no label.

Assuming ordinary labels average 100 UTF-8 bytes, a 100-item result adds roughly 10 KB plus JSON overhead. The name contract permits 128 KiB, so the pathological result is approximately 12.5 MiB; requests remain bounded, but this is a known response-size limit to observe before raising page sizes. At 100 maximum-sized related-list requests per second, the worst candidate budget is 500,000 rows per second, with at most 10,000 returned labels. This is a planning envelope, not a measured throughput claim. Keep API and database concurrency bounded; monitor response bytes, statement latency, read buffers and pool wait time. The target p95 is 250 ms for ordinary labels on a warm target; production qualification must measure representative visibility and alias skew at the provisioned concurrency.

No whole-corpus maintenance, offset pagination, recurring rebuild, in-process corpus cache or new migration is introduced. The query carries each owner identity explicitly, so a future owner-ID partition/shard router can route each bounded batch. Such a cutover needs its own concrete FK, migration and recovery qualification. The local HTTP fixture checks readable release and episode labels alongside permissions, revisions and pagination; it does not certify production throughput at 500 million or 3 billion rows.
