# REZICS 1.10.0

REZICS 1.10.0 atomically moves the API runtime to Elysia 2, TypeBox 1, and
Better Auth 1.7.2. It also replaces the project's Effect-only error hierarchy
with Elysia `HTTPError.id` while preserving the existing REZICS error envelope.
No mixed Elysia 1/2 or TypeBox 0/1 application build is supported.

The reviewed runtime matrix is Elysia `2.0.0-beta.10`, `@elysia/cors` and
`@elysia/openapi` `2.0.0-beta.1`, TypeBox `1.3.20`, Better Auth and its first-party
packages `1.7.2`, Better Call `1.4.0`, and Bun `1.4.0`. The Elysia packages are
pre-release software and remain exact pins.

## OpenAPI and generated clients

The generated OpenAPI document retains every path, method, operation ID,
security declaration, quota extension, request media type, parameter location,
and response status from the preceding release. The Elysia 2 adapter also
preserves the 27 named public schema components and emits resolvable references
for recursive documents.

TypeBox 1 produces a few intentional representation changes. Decoded integer
values are now documented as integers instead of a string-or-integer coercion
union, so generated response types narrow those values to `number`; URL query
and path serialization remains unchanged. String literal unions use an `enum`,
and repeated named documents use component `$ref` values instead of being
expanded inline. Empty tuples are normalized to arrays with `maxItems: 0` so
OpenAPI client generators do not infer `void[]`. These are the approved schema
expression differences for this migration; they do not add or remove an API
operation or wire response variant.

## Better Auth identity cutover

Better Auth 1.7 requires `accounts.issuer` and uniqueness over
`(issuer, account_id)`. The only configured account provider before this
cutover is email/password, whose existing rows map from provider `credential`
to issuer `local:credential`. Better Auth 1.7.2's published runtime and types do
not expose an `account.identityStrategy` option; REZICS therefore does not force
the newer documentation-only setting into this pinned release.

The migration is deliberately additive and backward compatible:

1. Run the read-only inventory before changing the database:

   ```sh
   task services-main:auth-identity:cutover-check -- preflight
   ```

   `DATABASE_ADMIN_URL` is required. The check uses the existing
   `(provider_id, account_id)` B-tree with two bounded range probes and refuses
   any legacy provider other than `credential`. Resolve unexpected providers
   with a separately reviewed issuer mapping; do not bypass this gate.
2. Confirm the disk, WAL, replica, and index-build budgets below. Run the
   migration during a low-write period and monitor
   `pg_stat_progress_create_index`, free disk, WAL growth, and replica replay
   lag. The normal `services-main:db:migrate` task runs the preflight, applies
   the migration with a five-second lock timeout and no statement timeout, and
   performs the read-only postcondition check.
3. `20260830064816_better_auth_1_7_identity.sql` adds the non-null column with
   the constant default `local:credential` and changes the API-key rate-limit
   default to the configured value of 5000. PostgreSQL stores the constant as
   missing-value metadata, so this step does not rewrite the accounts heap.
4. `20260830065046_better_auth_1_7_identity_index.sql` builds the new unique
   index with `CREATE UNIQUE INDEX CONCURRENTLY`. The old provider identity
   index remains available to the preceding application version.
5. After the concurrent index is valid, stop every process that can write
   authentication data and take a final restorable snapshot. Run the schema
   verification, deploy the 1.10.0 backend and lockfile to every instance as
   one unit, run the auth smoke matrix, and only then reopen writes. Never run
   pre-1.7 and 1.7 authentication writers at the same time. Deploy the
   generated API clients and web application after the backend. Do not enable a
   social account provider during the rollback window.
6. Repeat the schema postcondition explicitly if needed:

   ```sh
   task services-main:auth-identity:cutover-check -- verify
   ```

Better Auth's runtime schema generator is a verification input only. It never
applies production DDL.

The compatibility default and old provider index remain for one root-release
rollback window. A later reviewed migration may drop them only after 1.10.0 is
accepted and rollback to the preceding authentication binary is no longer
required.

## Capacity and operational model

The `accounts` relation is planned at 500,000,000 rows and estimated at
3,000,000,000 rows. Existing rows are expected to be entirely credential
accounts; the preflight proves that invariant without an exact count. Planning
traffic is 25,000 identity lookups/s sustained with 100,000/s bursts and 5,000
account writes/s sustained with 20,000/s bursts. Request-path access is one
exact equality lookup on `(issuer, account_id)` or a bounded `user_id` lookup;
there is no offset pagination, fan-out, or corpus scan. The database lookup
target is p95 below 20 ms at normal load.

These are capacity inputs, not benchmark results. Before a production table
approaches either planning point, replace them with measured row widths,
`pg_relation_size`, storage throughput, write rate, and replica bandwidth from
that environment.

| Cost | 500 million rows | 3 billion rows |
| --- | ---: | ---: |
| Logical issuer payload as rows are later rewritten, at 20–24 bytes/row | 10–12 GB | 60–72 GB |
| New B-tree at 96–160 bytes/entry, including fill-factor and page overhead | 48–80 GB | 288–480 GB |
| Two concurrent heap scans at an assumed 256-byte account row | about 256 GB read | about 1.54 TB read |
| Required build headroom at 2.5 times the estimated final index | 120–200 GB | 720 GB–1.2 TB |
| Planning WAL envelope at one to two times the final index | 48–160 GB | 288–960 GB |

The metadata-only column addition still needs a brief `ACCESS EXCLUSIVE` lock.
The five-second lock timeout makes it fail and retry instead of queuing behind a
long transaction. The concurrent unique index takes two table scans and waits
for conflicting snapshots, but does not block ordinary inserts, updates, or
deletes. Only one concurrent index build may run on `accounts` at a time.

Keeping both identity indexes temporarily adds one B-tree insertion per account
write. At the planning rate, the raw additional leaf traffic is approximately
0.5–0.8 MB/s sustained and 2–3.2 MB/s at burst before WAL and page-split
amplification; reserve two to four times those values for WAL. The shared
`local:credential` prefix and time-ordered account IDs can concentrate writes
on the right edge of the B-tree, so monitor page splits, buffer hit rate, WAL
bytes/s, and lock waits. Bound maintenance memory so parallel maintenance
workers together consume no more than 25% of database RAM.

Start only when free space exceeds the build-headroom estimate and primary plus
replica WAL capacity covers the planning envelope. Cancel the build if free
space approaches the operational reserve, replica lag exceeds the platform's
recovery-point objective, or foreground auth latency/error budgets are
breached. A failed concurrent build may leave an invalid index: inspect
`pg_index`, drop `public.accounts_issuer_account_id_key` with `DROP INDEX
CONCURRENTLY`, correct the cause, and retry before deploying 1.10.0.

At the 3-billion-row estimate, a single-cluster build may take many hours and is
accepted only after a production-equivalent throughput benchmark. If projected
index size exceeds 70% of the available storage budget, sustained p95 exceeds
20 ms, or replica/WAL capacity cannot absorb the build, stop the cutover. The
scale-out path is a separately reviewed identity-directory migration sharded by
a stable hash of `(issuer, account_id)`, with dual writes, per-shard unique
indexes, key-routed lookups, and keyset verification before read cutover. The
new identity tuple is deterministic and therefore does not impose a fixed
single-node addressing ceiling.

## Application verification and canary

Before promotion, run the deterministic TypeScript, schema, main-service,
OpenAPI, CORS, authentication, error-envelope, quota-cleanup, i18n, and
observability gates on the pinned Bun runtime. Smoke startup/readiness/health,
an anonymous route, an interactive-session route, an API-token route, a
validation error, a masked 500 response, Better Auth sign-in/sign-out and API
keys, and a credentialed CORS preflight.

Compare staging and canary success rate, p50/p95/p99, 5xx, validation and auth
failures, quota leases outstanding, completed spans, event-loop delay, and
memory against the preceding release. Stop promotion for an unexplained 0.2
percentage-point increase in 5xx/auth failures, a greater than 10% p95 or p99
regression, leases that do not return to baseline, incomplete spans, or
sustained memory growth.

## Rollback

The immediate rollback unit is the complete preceding application and lockfile.
The additive schema is safe for that binary: it ignores `issuer`, the old
provider index remains, and the credential default supplies the column for old
inserts. Stop every 1.7 authentication writer before redeploying every old
instance, and do not reopen writes until the old fleet is homogeneous. Prefer
this code rollback and leave the schema in place while the incident is
investigated.

If an operator must reverse the schema after the old binary is stable, first
prove that no non-credential accounts were created, retain a database snapshot,
then drop the new index concurrently, drop `accounts.issuer`, and restore
`apikeys.rate_limit_max`'s default to 300. Never drop the column while a Better
Auth 1.7 process can write. If the concurrent index migration itself fails,
remove only its invalid index and retry; the additive column remains compatible
with both application versions.
