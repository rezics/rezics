# REZICS 1.4.0

REZICS 1.4.0 replaces threshold-derived Unit reference states with factual
binary vote summaries. Alias and External Link resources no longer return
`accepted` or flat vote fields. They return `voteSummary`, support bounded
cursor pagination, and preserve withdrawn reference history. Unit Tag vote
mutations now return the same factual binary summary. The corresponding public
TypeScript client is `@rezics/api@1.8.0`.

This is a breaking API and persisted-contract release. Follow the coordinated
cutover in [Vote and reference governance](1.4.0.md#vote-and-reference-cutover).

The database migration builds active-reference indexes concurrently, validates
binary aggregate parity, installs hard active/pinned limits, optimizes reference
aggregate updates, and removes withdrawn Aliases from search documents. Do not
run old and new API binaries against the migrated database at the same time.

A follow-up integrity migration closes six nullable `CHECK` paths, adds the
1,024-byte indexed fractional-position ceiling, repairs reference-limit locking
for direct `unit_id` moves, and leaves historical validation staged outside the
deployment transaction. See
[Data integrity and workload budgets](../architecture/data-integrity-and-workload-budgets.md).

The same unreleased 1.4.0 cutover also replaces content moderation reasons with
multi-rule content governance and multi-authority report referrals. Reports and
adverse decisions may cite multiple rules from the current Realm and the
official Rule Realm. Old moderation reports, cases, actions, notes, reasons,
notifications, and derived counters are intentionally discarded; there is no
data or API compatibility layer. Materialized Unit states and live account
enforcements remain authoritative. Deploy this change only as the coordinated
cutover documented in
[Content governance and reporting](1.4.0.md#governance-cutover).

Notifications now expose typed, recipient-authorized destinations and every
notification row navigates to its corresponding feature or to a safe
recipient-only detail page. Clicking an unread row navigates immediately while
marking it read optimistically. Mark-all uses a per-recipient read-through
watermark instead of rewriting inbox history, and the Web badge no longer
renders estimation notation. This is a coordinated API, generated-client, Web,
and database cutover; follow
[Notification delivery and read state](1.4.0.md#notification-cutover).

## Governance cutover

This section preserves the named historical release procedure. It is not an instruction for the current installation baseline.

1. Stop all pre-1.4.0 API and worker processes. Mixed binaries are unsupported.
2. Back up the database for rollback of the whole deployment, not for importing
   old moderation data into the new model.
3. Apply `20260809000003_content_governance_rewrite.sql`. It preserves current
   materialized Unit and Realm Unit states and live account enforcements, then
   drops old report, case, action, reason-bearing, aggregate, trigger, note, and
   notification data.
4. Deploy the 1.4.0 API, generated clients, web application, and workers as one
   coordinated release.
5. Run migration/schema synchronization, seed-contract, aggregate
   reconciliation, and representative queue-plan checks before reopening
   reporting.

Rollback means restoring the pre-cutover backup and the complete pre-1.4.0
binary set. There is intentionally no reverse data migration and no dual-write
period.

## Notification cutover

This section preserves the named historical release procedure. It is not an instruction for the current installation baseline.

The API response changes from a raw payload bag to the correlated
`context`/`destination` contract, and read mutations return an idempotency result
with the effective read timestamp. Deploy the API, generated clients, and Web
application together.

1. Stop pre-1.4.0 API and worker writers and take the deployment rollback
   backup.
2. Apply `20260811000000_notification_read_through_state.sql`. It adds only
   nullable state columns, installs staged checks, and replaces the recipient
   aggregate trigger; it does not rewrite the notification corpus.
3. Deploy the 1.4.0 API, regenerated clients, Web application, and workers as
   one coordinated release. Do not run mixed response contracts.
4. Verify recipient scoping for conversation/report/invitation destinations,
   mark-one idempotency, the insert-versus-mark-all race, aggregate parity,
   recipient lock waits, and replica lag.
5. Validate the two staged recipient-state checks with the integrity-constraint
   command after confirming maintenance I/O headroom, then resume writers.

Rollback means restoring the pre-cutover backup and complete pre-1.4.0 binary
set. The nullable columns require no data backfill, but there is no public API
compatibility alias for the removed payload response.

## Vote and reference cutover

This section preserves the named historical release procedure. It is not an instruction for the current installation baseline.

This is a breaking public-contract release: product version `1.4.0` and API
client version `1.8.0`.

1. Deploy clients that read `voteSummary` and do not use `accepted`, flat
   reference vote fields, or a `candidate` resource name.
2. Pause writes or drain the old API binary. Apply
   `20260809000000_vote_reference_contract.sql` followed by
   `20260809000001_vote_reference_indexes.sql`; nullable columns are metadata
   only, parity constraints are added `NOT VALID` before transactional online
   validation, and replacement indexes build concurrently in the second step.
3. Deploy the new API and frontend together. Old binaries are incompatible
   with the new response shape, pagination, and withdrawal endpoint.
4. Verify reference-limit conflicts, cursor invalidation, aggregate parity,
   search exclusion after Alias withdrawal, destination-capacity enforcement
   when a row's `unit_id` changes, lock waits, and replica lag.
5. Resume writes. Rollback requires the previous binary and a database restore;
   the public contract and withdrawn-reference lifecycle do not have a mixed-
   version compatibility alias.
