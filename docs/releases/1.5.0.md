# REZICS 1.5.0

REZICS 1.5.0 makes Realm Rule authoring multilingual and non-destructive. Each
Rule in a replacement revision now carries a non-empty `localizations` array,
and the authoring read endpoint returns every stored localization. The web
editor keeps language-specific and shared drafts independently, persists them
in versioned browser storage, detects a newer server baseline, and supports
moving Rules up or down before publishing the next revision.

This is a breaking public API release. `PUT /api/v1/realms/{realmId}/rules`
removes the single Rule-level `language`, `title`, and `content` fields. It
requires `baseRevisionId` and accepts `localizations[]` for every Rule. The
matching public TypeScript client is `@rezics/api@1.9.0`.

No database migration is required: Rule content already uses the shared
`unit_localization` relation, whose `(unit_id, language)` identity supports the
new contract. Existing single-language Rule revisions remain valid and appear
as one-element localization arrays. Deploy the API, generated clients, and web
application together by following the coordinated cutover in
[Multilingual Realm Rule authoring](1.5.0.md#rule-authoring-cutover).

## Rule authoring cutover

This section preserves the named historical release procedure. It is not an instruction for the current installation baseline.

1. Stop Rule authoring during deployment. Mixed 1.4.0 web/API/client binaries
   are unsupported because their PUT bodies have different meanings.
2. Back up the database. No schema or data rewrite is needed; verify that the
   existing `unit_localization` primary key and ordering indexes are present.
3. Deploy REZICS 1.5.0 API and workers, the generated OpenAPI clients including
   `@rezics/api@1.9.0`, and the 1.5.0 web application as one release.
4. Verify that a current one-language revision loads as a one-element
   `localizations` array, publish a two-language revision, reload both languages,
   and verify the submitted Rule order.
5. Re-enable Rule authoring after API and web release headers both report
   1.5.0.

Rollback requires the complete 1.4.0 binary and client set. Newly published
multilingual rows are readable by the old public fallback endpoint, but the old
authoring UI would overwrite them with one language. Keep Rule authoring
disabled after rollback until 1.5.0 is restored or an operator intentionally
publishes a replacement revision through a multilingual-capable client.
