# REZICS 1.11.0

REZICS 1.11.0 removes full Post bodies from canonical Feed projections and
precompiles the Elysia application before srvx accepts traffic. The release
also bounds each Feed item's attribution and public-Realm context fan-out.
Together these changes remove an observed multi-second response-validation
cliff from otherwise light Feed and Zone aggregate queries.

## Public API cutover

The `body` property is removed from every Post variant embedded in a canonical
Feed item. This affects the standard Feed, Search Feed, Review list, related
Posts, Collection content, Realm pins, and Zone Feed/aggregate responses that
share that projection. Post detail and reply-tree contracts keep their bodies.

Consumers must switch atomically with the 1.11.0 contract:

1. Regenerate clients from the 1.11.0 OpenAPI document.
2. Remove Feed-card and pinned-content reads of `item.body`; render the authored
   `summary` when present and omit preview copy when it is absent.
3. Fetch `GET /api/v1/posts/:postId` only after a user opens a Post or another
   workflow explicitly needs the full document.
4. Deploy the backend first, then the generated clients and web application in
   the same maintenance window. Mixed 1.10.0/1.11.0 public clients are not a
   supported steady state.

There is no persisted-data or database-schema migration, no backfill, and no
dual-read compatibility field. The authored body remains unchanged and
available from Post detail endpoints. Rollback redeploys the complete 1.10.0
backend, generated clients, and web application; no data reversal is required.

## Runtime and capacity model

The server calls `api.compile()` after all conditional routes are registered
and before `srvx.serve`. Startup performs validator code generation once;
requests no longer depend on Elysia's deferred validation threshold. If startup
compilation fails, the process fails before readiness and receives no traffic.

Feed hydration no longer selects `unit_localization.content`. It reads at most
50 candidates per ordinary page, 8 ordered attributions per item, and 8 public
Realm contexts per item. Zone aggregates remain bounded to 20 eager items per
Block, 24 Page query Blocks, and 6 Dock query Blocks. The association probes use
existing `(source_unit_id, position, id)` and
`(unit_id, publication_state, status, updated_at, realm_id)` indexes with a
lateral `LIMIT`, so one high-degree Unit cannot force a complete association
scan or application-memory fan-out.

Capacity planning assumes 500,000,000 rows in each corpus-scale relation and a
3,000,000,000-row estimate. The request work is keyed by at most 50 candidate
IDs and fixed per-item limits, so corpus growth increases B-tree depth rather
than request fan-out. A typical 100 KiB Post body previously added up to 5 MiB
per 50-item Feed page and about 500 MiB of transient body payload at 100
concurrent requests, before object and serialization overhead. Body size was
not contract-bounded, so the true previous worst case was unbounded. The new
projection's authored summary is limited to 2,000 characters at write time.

No request-path cache, background queue, whole-corpus scan, offset pagination,
or recurring recomputation is introduced. There is no write amplification or
maintenance migration. Monitor startup duration, readiness failures, response
bytes, API process RSS, event-loop delay, and Feed/Zone p50, p95, and p99. Stop
promotion for failed startup compilation, sustained memory growth, or an
unexplained response-latency regression greater than 10% against 1.10.0.

## Verification and rollback

Release gates are backend and frontend TypeScript checks, focused Feed/schema
tests, generated-client checks, a representative `EXPLAIN (ANALYZE, BUFFERS)`
for both bounded association probes, and a real Zone aggregate request using a
Post with a large body. The response must omit every Feed `body`, database work
must remain index-routed, and warm end-to-end latency must not show the former
multi-second validation plateau.

Rollback is application-only. Redeploy all 1.10.0 processes and clients as one
unit. Because 1.11.0 does not mutate persisted content or schema, rollback does
not require a database restore or reverse migration.
