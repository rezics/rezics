# REZICS 1.7.0 governance Rule cutover

REZICS 1.7.0 replaces human governance reason enums with immutable Realm Rule
decisions and introduces an optional Zone-local Rule Realm. This is a breaking
database, API, generated-client, and Console release, but it supports an
in-place upgrade of an installed 1.6 database.

## Historical boundary

The upgrade preserves Units, users, account state, enforcement actions,
content actions, access restrictions, merge requests, and audit events. It
does not translate or retain pre-1.7 governance reasons:

- `governance_reason_code`, `user_account_state_reason`, their columns, and the
  old content-action Rule attachment table are removed;
- no Rule, decision, outcome, or audit detail is fabricated from those values;
- a preserved pre-1.7 domain row has `decision_id = NULL`; and
- historical audit rows remain schema version 1, while new audit rows use
  schema version 2.

The nullable physical link is only a cutover boundary. Every 1.7 writer creates
a finalized `rules` or `reversal` decision and writes its non-null identifier
in the same transaction; database insert triggers reject new domain rows with
no decision. A pre-1.7 action without a decision cannot be used as an
exact-reversal basis. A pending pre-1.7 merge is superseded when reviewed and
must be proposed again with current Rules. Existing operational state is not
deleted or silently relaxed.

## Rule Realm ownership

Bootstrap owns the fixed official Rule Realm identity, membership, and access
policy. It does not own Rule revisions or Rule Units. Those are online product
history and are never compared with a repository manifest during preflight or
release.

A fresh installation runs the special official Rule initial Seed after
bootstrap. The Seed publishes starter content only when the Realm has no
revision; `--if-needed` treats any existing online revision as authoritative
and changes nothing. Routine upgrades never run that Seed. Later Rule changes
use the ordinary publication service and create new online UUIDv7 identities.

## Upgrade

1. Stop pre-1.7 writers and public traffic for the coordinated breaking
   release.
2. Take and verify a restorable physical backup.
3. Run database preflight. It verifies migration history and permanent
   platform identities, not mutable Rule content.
4. Apply migrations `20260811190001` and `20260811190002`. The first performs
   the metadata cutover and installs new-write constraints as `NOT VALID`; the
   second builds partial decision-reference indexes concurrently.
5. Reconcile privileges and run PostgreSQL, platform-core, governance, and
   canonical-index verification.
6. Deploy the 1.7 API, workers, generated clients, and web application as one
   unit before reopening traffic.

Rollback restores the backup and the complete 1.6 binary set. There is no
reverse data migration after 1.7 traffic has written decisions.

## Migration workload

The cutover performs no historical row rewrite or decision backfill. Adding
nullable columns and dropping obsolete columns are catalog operations; foreign
keys and replacement checks are installed `NOT VALID`, so new writes are
protected without scanning old rows inside the release transaction. The
release uses a five-second lock timeout rather than waiting indefinitely for
the short table metadata locks.

The six partial indexes contain only rows whose post-cutover decision link is
non-null and are built one at a time with `CREATE INDEX CONCURRENTLY`. PostgreSQL
still reads each source relation while building an index. Planning therefore
assumes up to 500 million rows per corpus relation and treats 3 billion rows as
a sharded/partitioned forward case. For an illustrative 0.30 KiB average audit
row, one 500M-row heap is about 143 GiB and one 3B-row heap about 858 GiB before
TOAST and free space; a concurrent build can read the heap more than once, so
operators must budget roughly 286 GiB or 1.7 TiB of sequential read I/O for
that relation. Actual `pg_total_relation_size`, primary I/O, WAL, replica lag,
and index progress are the release inputs; pause or reschedule if sustained I/O
exceeds 70% or replica lag breaches the deployment SLO. At the 3B boundary,
build per partition or shard instead of treating one primary as the target.

The partial predicate makes the resulting index size proportional to new
decision-linked rows rather than historical corpus size. Write amplification
after cutover is one small UUID index entry per affected domain write; audit
and decision history reads remain bounded by their existing keyset indexes.
