# REZICS 1.9.0

REZICS 1.9.0 introduces the significant persisted and public contracts for
Zone composition, aggregate Block execution, semantic theming, and reviewed
full-trust Custom Themes. The matching backend and web release is 1.9.0. The matching
breaking public TypeScript client release is `@rezics/api@1.11.0`.

This release supports v1.0.0-and-later data only and introduces no compatibility
alias for the superseded bare-Block-key execution routes or globally scoped
Block-key assumptions.

## Cutover order

1. Stop writes that create or replace Zone Pages, main Docks, Custom Themes,
   Unit presentation documents, installations, and
   Book metadata. Keep ordinary reads available if the deployment platform can
   guarantee that old processes do not write the affected contracts.
2. Apply `20260829103742_custom_theme_capability_values.sql` outside a
   transaction, then
   `20260829103743_custom_theme_full_trust_external_resources.sql`, followed by
   the remaining 1.9.0 migrations beginning with
   `20260829134649_tag_path_semantic_model.sql`. PostgreSQL must commit the new
   enum values before constraints can reference them. The migrations add the
   generic `custom_theme` Unit, immutable package/review history,
   external-resource monitoring, exact installations, Unit-owned Header/Footer
   presentation history, narrow access lifecycle, viewer preference, global
   execution control, the semantic tag-path model, and bounded queue indexes.
3. Deploy the 1.9.0 backend before the web client. The backend accepts and emits
   `BlockPath`, sibling-local Block keys, list presentation profiles, pinned
   sorts, derived sources, semantic style roles, extended theme tokens, and the
   generic Custom Theme, presentation, installation, and review APIs.
4. Regenerate and deploy the OpenAPI clients and then the 1.9.0 web application.
   The Zone Page performs one render projection read and one aggregate execution
   request; per-Block continuation remains available.
5. Resume writes after smoke checks confirm Page/Dock reads, Book status
   filtering, theme fallback, and the review queue. No dual-write period is
   supported: the previous backend is intentionally incompatible with the new
   persisted contracts.

Showcase packs are never part of production cutover. They are disposable local
development fixtures; REZICS canonical rows and REZICS-owned history are the
sole production source of truth.

Before accepting submissions, provision separate reviewer, external-live
access-management, and emergency-kill authorities and follow
[external-live access governance](../operations/custom-theme-external-live-access.md)
and [Custom Theme review and incident response](../operations/custom-theme-review-and-incident-response.md).
Development databases that applied the superseded unreleased preview migration
must follow the [development cutover note](../operations/custom-theme-development-cutover.md).
The backend database pool must contain at least three connections; aggregate
Zone execution admits at most `DATABASE_POOL_MAX - 2` concurrent Block jobs so
ordinary request traffic retains two connections.

## Persisted contract changes

- Block `_key` uniqueness is sibling-local. Query Blocks are addressed by a
  keyed structural `BlockPath` within the Page or Dock selected by the route;
  resource UUIDs are not copied into document JSON.
- Zone Page, Dock, and Wiki policies enforce their own depth, Block-count, and
  query-Block budgets. Page/Dock aggregate scheduling is a runtime cap and is
  never a cross-document write invariant.
- `book.release_status` becomes a typed Filter predicate supported by the
  `(release_status, id)` index.
- `custom_theme_revision` stores immutable manifest/package identity,
  host-full-trust execution state, host-scoped approval, review evidence, and
  kill state. Files, review events, and external-resource observations retain
  immutable history; keyset workers monitor mutable remote dependencies and
  fail closed into revalidation without installation scans.
- `unit_presentation_document` owns generic Header/Footer Block regions with
  immutable revision history. `unit_custom_theme_installation` pins one exact
  approved revision for a registered top-level host and target contract.

## Operational rollback

Before applying the migration set, application rollback may redeploy the
previous processes. After migration, rollback requires restoring the matching
pre-migration database snapshot together with the previous binaries; otherwise
roll forward. The previous application does not understand the new persisted
contracts. Killing a theme revision, uninstalling one host, disabling custom
themes for a viewer, using safe mode, or activating the global execution switch
is the supported immediate presentation rollback and preserves token fallback.
CSS-only preview approvals are not inherited by host-full-trust revisions.
