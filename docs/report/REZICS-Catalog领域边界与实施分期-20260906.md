## 1. 如何区分决定与交付状态

本文中的“采用”说明模型方向，不表示已经上线，也不自动将全部未来领域纳入下一次实施任务。

| 标记 | 含义 | 后续实施时如何使用 |
| --- | --- | --- |
| **当前基础** | 2026-09-06 核对到的源码结构 | 只证明所列代码或结构存在，不证明完整产品能力或生产容量 |

## 2. 统一拆分规则

**已确认，待实施：按对象的身份规则和业务结构划分模型，按数据的增长与访问方式划分存储。分类名称不直接决定表或数据库。**

### 2.1 五种不同的决定

| 观察到的差异 | 应作的决定 | 示例 |
| --- | --- | --- |
| 只有分类不同，结构和操作相同 | 共用模型，用语义类别或关系区分 | 编辑器、游戏、软件插件；动画与真人节目 |
| 同一对象有稳定专属结构 | 增加同 ID 扩展或类型化子表 | 产品型号增加显卡规格；服务增加计算规格 |
| 被指称对象不同，有独立身份和生命周期 | 建立关联对象；是否另建物理表再按结构决定 | 型号与实物；课程与开课；内容与平台投稿 |
| 资料、来源、历史、关系和查询有独立维护负载 | 建立明确拥有者的表组 | 图片编目、包发布及依赖 |
| 同一种记录增长到需要独立维护或扩容 | 分区、分片或迁出原有表组 | 数十亿图片仍属图片；大型包生态可占多个分片 |

字段数量与空值比例可以帮助识别问题，但不是唯一判据。长尾属性通常先使用有类型的动态属性；稳定约束、高频筛选或执行行为要求专属结构时，再确定扩展表。字段与关系的权威规则见[结构与查询报告 §2](REZICS-内容结构关系与查询模型-20260906.md#2-字段对象与物理表分别作决定)。

### 2.2 接入新领域的判断顺序

1. 写清用户究竟在识别、收藏、评价和引用什么，包括外部 ID 的命名空间、身份范围和变更规则。
2. 找到可以复用的已有结构；不要因新类别名称出现就新增根类型、表组或服务。
3. 区分对象属性、组成位置、关系语境、独立对象和技术资源；不靠一列 `kind` 掩盖不同身份。
4. 确定新约束及操作：只增分类、增加规格扩展，还是新增版本、兼容、场次等领域契约。
5. 为每项当前值、来源事实、修订和投影指定唯一写入拥有者，列出必须同事务修改的数据。
6. 估计每种记录的数量、倍增系数、更新率和访问路径，再决定其物理表与未来迁移边界。

这不是先列尽世界上的所有类别再开始开发。新增普通语义类别可以复用既有结构；新增可执行行为需要实现与验收。领域分析与部署划分也应分别进行。[Microsoft 领域分析指南](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/domain-analysis)

## 3. Catalog 全领域归属地图

### 3.1 Catalog 是上层编目能力

**已确认，待实施：** Catalog 指全部被索引对象的编目能力，不专指书籍，也不意味着一个总表或总数据库。书籍出版表组使用 `publishing` 作为职责名称，不再以 `catalog` 与其余领域并列。

本文表名和表组名均为职责示意，不是已发布 SQL、API、`unit.kind` 或兼容别名。具体实施仍使用仓库要求的 `public` schema、snake_case 和受类型检查的模块；此次命名整理不重命名现存数据库对象。

### 3.2 建议表组与启用条件

下表各边界的方向已确认；“交付范围”单独说明实现状态。表组不要求对应单独的进程、数据库或开发团队。

| 表组 | 负责的领域结构 | 边界及交付范围 |
| --- | --- | --- |
| 书籍出版 `publishing` | 具体读本／出版版本、文本资料、按需识别的内容身份 | **当前基础＋待实施。** 复用 Book；不强制 Work；书籍变成可售商品也不迁走出版身份 |
| 音乐 `music` | 发行组、发行、录音及按需乐曲对象 | **待实施。** 是完整承载 MusicBrainz 的目标；载体和 Track 位置复用结构，不能声称当前 Audio 已覆盖 |
| 影视节目 `program` | 影片、节目、季、集、必要剪辑版本及演职资料 | **当前基础＋待实施。** 从现有 Media 的实际粒度迁移；角色不同不自动要求每种一张空表 |
| 图片内容 `image` | 图像内容／版本、图片集、领域资料 | **未来按需。** 独立内容表组和重索引；配图资源不自动升级为独立摄影作品 |
| 视频内容 `video` | 视频内容／版本、字幕与内容资料关联 | **当前 Video 基础＋未来扩展。** 可独立扩展其重资料；不把影视语义、平台投稿与文件压成一个对象 |
| 软件 `software` | 软件项目、用途、宿主和功能扩展关系 | **当前基础＋待实施。** 插件仍可属于软件；完整宿主、版本兼容与生态能力尚未交付 |
| 包与发布 `package` | 注册表坐标、包版本、依赖、产物关联 | **未来按需。** 可承载软件、AI 权重、地图和资源包；接入实际协议时交付专属契约 |
| 3D `model3d` | 模型、修订、几何／材质／骨骼等资料 | **未来按需。** 几何资产与 AI 权重的含义不同；共用分发机制不共用完整领域模型 |
| AI 模型 `ai_model` | 模型、权重版本、变体、血缘、模型卡与评测关联 | **未来按需。** 与代码项目、文件和推理服务分别建立关系 |
| 实物产品 `product` | 产品型号、变体、必要实物个体 | **未来按需。** GPU／家具可共享产品结构，规格扩展；不吞并书籍、软件等已明确的领域身份 |
| 服务 `service` | 服务定义、规格、提供者、必要服务实例 | **未来按需。** 计算服务使用规格扩展；调度、库存时序与计费不归编目主行 |
| 教育 `education` | 课程、开课、学校／教师关系及教学资料 | **未来按需。** 不按学校建表；课程代码按所属机构及有效语境识别 |
| 事件与活动 `event` | 事件、活动系列、场次、时间、地点与参与关系 | **Current stage for MusicBrainz-required catalog data.** Broader event products remain future scope; distinguish event identity, place/time and repeated occurrences. |
| 公开主体 `entity` | 人、组织、角色、服务代理及获授权的互动资料 | **当前基础＋待实施。** Profile／Entity 合并尚未完成；平台账号与实际创作者身份分开 |
| 网站与平台资料 | 网站、平台账号、外部发布及来源身份 | **未来按需。** 网站不必是软件；跨内容类型共享协议，不强制所有重投稿数据汇入一个表 |
| 组织对象与一般概念 | 系列、世界观、IP、地点及其他受治理概念 | **部分基础＋待实施／未来扩展。** 复用组织／类成员机制；普通新概念不要求专属空表或互动权限 |

资产、来源机制、权限、标签、收藏和社群是这些领域共用的能力。共享机制不表示所有实例数据都要保存在一个永久的全站大表。

### 3.3 交叉对象与单一事实权威

一个对象可以属于多个语义类、组合多个资料扩展；同一个物理字段或事实不能由两个模块独立修改。需要区分三个概念：

- **语义类别**回答对象是什么或具有什么作用，可以多个。
- **写入拥有者**回答哪一个模块维护某份事实，不等同于用户访问权限中的 owner。
- **存储归属**回答数据目前放在哪个表组或路由桶，可经显式迁移改变，不从可编辑标签临时推导。

例如同一段 MV 内容可以组合视听资料与音乐关系；确实独立的录音对象仍有自己的 ID。给软件增加“可销售”资料，不新建一份同名 Product 复制其标题、作者和版本。归属规则在具体对象契约中固定，不能由哪个导入器先写入随机决定。

需要同事务维护的同 ID 扩展在同库阶段使用真实外键。未来迁出时明确哪些扩展必须随对象同行、哪些是独立关联对象；这不是现在部署跨库事务的理由。

## 4. 关键领域的具体界限

**本节是已确认方向的领域示例；除 §1.1 列出的当前基础外，新增结构均待实施或未来按需。代码块不构成可直接执行的 DDL。**

### 4.1 实物商品与 GPU

同一个显卡型号可以使用以下结构：

```text
unit(id = U)
  product_model(id = U)          厂商、型号等产品资料
  graphics_card_spec(id = U)     显存、接口、板卡专属规格

另一个对象 C：GPU 芯片型号
  U --采用芯片--> C

另一个对象 I：某一张可识别实物显卡
  I --属于型号--> U
```

同 ID 的 Unit 扩展仍以 `id` 为主键并直接外键引用 `unit.id`；需要同时满足产品资格的约束由实施契约补齐，不能假设一个 Unit 外键就证明规格适用性。基础字段只有一个归属；不要在规格表再复制厂商名称和标题。

一般产品、GPU、CPU、主板不因名称不同就各建一套完整平台。专属规格使用扩展；长尾规格使用有类型动态属性。硬件型号、兼容关系、评测若形成独立维护负载，再整体扩展硬件表组。

型号、变体与实物的身份不能互换。Schema.org 分别定义产品型号和单个可识别实物，可作语义参考，不能直接替代本地约束设计。[ProductModel](https://schema.org/ProductModel)、[IndividualProduct](https://schema.org/IndividualProduct)

“商品”也是商业视角：书籍、软件、课程和服务都可能被交易，不因此强制成为另一份 Product。Market 引用相应身份；型号评价、实物状况、卖家服务评价有各自范围。

### 4.2 算力、服务与运行记录

| 被描述对象 | 归属 | 不应混入的内容 |
| --- | --- | --- |
| 供应商提供的计算实例规格 | `service_spec`＋`compute_spec` 等同 ID 领域扩展 | 每分钟剩余数量、每次运行和账单 |
| 具体集群、资源池或节点 | 必要的独立资源身份，关联服务和硬件 | 不假设服务必然公开全部物理拓扑 |
| 某次性能测试 | 带版本、任务、精度、环境及来源的测量记录 | 不混成无条件的“算力”数字 |
| 可用量、利用率、任务执行 | 独立运行／测量数据模块 | 不为每个采样创建完整 Catalog Unit |

服务定义描述供应者提供的能力；服务实例、硬件和测量结果各有生命周期。[Service](https://schema.org/Service) 仅提供服务语义参考。

Catalog 可以索引并讨论服务和资源；实时库存、容量预约、调度、计量与交易必须由各自的领域操作维护。索引一个外部算力服务，不要求 REZICS 同时实现其调度器。高频记录需要独立保留期和存储预算，不借本次 Catalog 改造提前建立完整计算平台。

### 4.3 软件、插件、包与文件

| 概念 | 推荐语义 |
| --- | --- |
| 软件项目 | 持续可识别的软件；可以是应用、库、插件或游戏 |
| 插件 | 扩展某个宿主的作用及关系；适配条件可能具体到版本和环境 |
| 包 | 某个分发体系中的发布／安装身份；不是软件项目或压缩文件的同义词 |
| 包版本 | 该包的一次具体版本身份；版本规则服从生态，不统一强制 SemVer |
| 产物 | 可取得的文件或内容；一个版本可关联多个平台、格式的产物 |

包坐标的候选身份包含注册表／来源范围、生态、命名空间和规范化名称；最终唯一键、重命名及删除后复用规则必须按生态确定。保留原始名称与版本。镜像和多个渠道是否指向同一权威发布，依据来源映射判断，不仅按名称或文件摘要合并。

项目、包和代码仓库不强制一对一；只有包资料时先收录包，不凭空制造上层项目。包也可以关联 AI 权重、地图和纹理等内容，因此包发布机制可跨领域复用。软件依赖与安装兼容使用有类型领域契约；统一关系读取不产生另一份可独立编辑的依赖事实。

deps.dev 分开暴露 Package、Version、Project、Requirements 等接口，并说明不同生态的名称规范化和来源覆盖差异，支持上述分层，但不证明 REZICS 已实现这些协议。[deps.dev API](https://docs.deps.dev/api/v3/)

### 4.4 网站、Web 软件与部署实例

Web 应用可以复用软件项目模型；学校官网、作者博客等网站不因使用软件搭建而必须拥有软件项目或包。一个软件的桌面版与 Web 版是否共用项目身份，按实际产品范围确定。

软件项目、某组织部署的服务、承载内容的网站以及域名／URL分别表达。域名和访问地址可以变化，不代替稳定 Unit ID；同一对象具有多种呈现能力也不要求机械制造多份条目。[WebApplication](https://schema.org/WebApplication)、[WebSite](https://schema.org/WebSite)

### 4.5 图片、视频、外部投稿与资源

```text
图像或视频内容／明确版本
  → 某个平台上的发布／投稿（保留来源身份）
  → 被引用的原文件、预览图、字幕或转码资源
```

这些层次分别识别。来源仅提供投稿时，可以先形成薄来源对象，之后有依据再关联内容身份；不强制每次导入都额外制造一个抽象 Work。投稿可能包含多张图或多段内容；组成和顺序由内容结构表达。

图片与视频各自拥有可扩展的内容资料、来源历史和必要索引；采集器、来源协议和资源登记可共享。跨域投稿可以有混合内容，不能靠“首张图片／首个视频”永久决定其全部语义。

商品配图或缩略图可先作为资源引用；需要独立编目摄影／插画作品时建立相应内容身份。转码、镜像和缩略图不是自动新增的作品。现有 Audio／Video 是 Unit，不能在迁移中直接重新解释为文件记录。内容与编码资源的区分参考 [MediaObject](https://schema.org/MediaObject)。

创作者 Entity、平台账号和投稿分别引用；上传者不自动等于创作者。删除一个来源投稿也不自动删除其他来源、内容身份或用户讨论。

### 4.6 AI 模型与 3D 内容

二者都可能有项目、修订、文件和分发包，但各自的领域结构不同。AI 模型需要模型血缘、任务、权重变体及评测语境；3D 内容需要几何、材质、骨骼、比例和使用环境等资料。稳定结构按领域定义，未知或长尾属性使用有类型扩展。

模型权重、实现代码、推理服务和评测运行不是同一个对象；一份 3D 内容、其格式转换文件、材质引用和预览图也不是同一个粒度。共享包发布、资源登记与来源机制，不共享一张包揽全部字段的 `model` 表。具体版本等价、格式与指标单位的规则留给各自启用时的实施契约。

### 4.7 课程、开课、事件与场次

课程定义与某学校、学期、班次中的实际开课分别识别；不按每所学校建立物理表，不将课程代码视为全球永久唯一。课程名、课程代码、修订和机构映射的具体规则按来源确定。开课可关联教师、时间、地点和课程资料；课程录像引用视频内容，而不是塞进课程主行。[CourseInstance](https://schema.org/CourseInstance)

开课与活动场次可以共享必要的时间／地点结构，但教学约束仍归教育领域。历史事件不强制先创建事件系列，重复举办的活动按需有系列与场次。被编目的事件也不同于系统审计事件、点击或采样记录。

## 5. 共享能力与可迁移的存储归属

**已确认，待实施：共享逻辑协议与平台能力；每份事实拥有明确主存，重记录允许独立增长。**

1. **稳定 Unit 身份。** 对独立引用、收藏、讨论和共建有意义的对象使用 Unit；规格扩展可与对象同 ID。依赖边、属性值、镜像、采样和文件分块不自动成为完整 Unit。新增对象的公开 API 与地址遵循[Unit 地址契约](../architecture/unit-slug-addressing.md)。
2. **稀疏能力。** 收藏、标签、评分、Issue、百科和讨论按真实使用产生行；不为每条包版本或来源投稿预建一套空内容。权限是否允许某动作由已实现能力决定，不由语义类别自动授予。
3. **局部数据包。** 表组拥有必要的当前资料、来源观察、修订、事实和检索投影；大型正文、文件及派生资源使用合适存储。不能只拆一个很薄的领域表，却把全部重文本、历史和索引写回同一个不可拆的公共容器。
4. **跨领域关系。** 一条关系有唯一主存拥有者；反向导航使用索引或可重建投影，不在每个端点保存两份可独立编辑的事实。稳定关系 ID、定义和修订契约沿用结构与查询报告；来源有冲突时保留来源事实，不制造虚假的一致性。
5. **模块选择受控。** 同构的来源、关系、修订和查询结构可共享 schema 模板；实际物理表由服务端受类型检查的登记选择，不允许用户参数拼接表名。当前 `unit.kind` 不是任意语义类别，也不直接等于物理分片地址。
6. **共置与跨组读取。** 同库阶段保留明确的 JOIN、事务和真实外键。未来迁出需要识别必须同行的扩展、修订与引用；跨组查询集中在有名字的读取接口。多种资料能力并不承诺未来所有跨域 JOIN 都免费。

`unit`、全局来源身份定位、标签及反向投影本身也计入容量。来源身份唯一性不能仅靠“UUID 不重复”代替；未来分片时必须设计唯一性的作用域和校验途径。详见[总体报告 §10](REZICS-动态元信息与渐进扩展架构-20260905.md#10-第一阶段的分表方案)。

## 6. 不均匀增长的规划与验证边界

**增长方向已确认；以下数值、访问画像和分片键均为规划输入，尚未压测或确定为最终 DDL。**

### 6.1 按记录种类估算，不按栏目平均分配机器

所有潜在全量数据集分别使用 5 亿行基线和 30 亿行估计；定义、类别成员和来源映射也不自动视为有界小表。以下是说明放大关系的假设，不是世界数据总量预测：

| 假设 | 增长结果 |
| --- | --- |
| 500 万包，每包平均 20 版本，每版本 8 条依赖 | 1 亿版本、8 亿依赖；仅项目数无法表达负载 |
| 5 亿／30 亿版本，每版本 8 条依赖 | 40 亿／240 亿依赖；子关系基线必须随实际放大，不封顶在 30 亿 |
| 每条内容平均关联 2 个来源发布、3 个资源引用 | N 条内容产生约 2N 发布和 3N 引用；另计修订、别名、语言与去重映射 |
| 1 万资源，每分钟 1 次采样 | 每日 1,440 万记录，365 天约 52.56 亿；不纳入 Catalog 主行更新路径 |

复用总体报告的部分假设行宽，仅演示数量级。数值包括假设的行与相关索引，不含正文、文件、WAL、备份、副本、维护余量和其他表；实施时测量真实宽度，不能重复计数。

| 记录族 | 假设合计字节／行 | 5 亿行 | 30 亿行 |
| --- | ---:| ---:| ---:|
| 薄 Unit 身份 | 240 | 120 GB | 720 GB |
| 来源映射或依赖记录的示例宽度 | 160 | 80 GB | 480 GB |
| 包版本示例宽度 | 512 | 256 GB | 1.536 TB |

GB／TB 为十进制。动态事实、媒体文本和全部领域总量按[总体报告 §13](REZICS-动态元信息与渐进扩展架构-20260905.md#13-动态模型与不均匀数据的容量预算)累计；表中宽度不代表所有来源或依赖都同宽。GPU 型号数量较少，也不能用它推断实物、兼容边和评测记录的数量。

### 6.2 访问与增长方式决定物理划分

| 数据族 | 主要访问／维护方式 | 候选扩展方向与偏斜约束 |
| --- | --- | --- |
| 产品型号、领域规格、课程定义 | 按对象取资料；按有类型规格或机构条件筛选 | 从对象 ID 共置扩展；规格检索单独设计，不按厂商或学校各建一张表 |
| 内容与外部发布 | 按内容／来源身份读取，按作者／账号反向分页 | 按内容或发布身份分散；反向索引另计；避免超级频道成为不可再拆的单个分片 |
| 包版本与依赖 | 按包列版本、按版本读依赖、反向依赖筛选 | 包内共置是候选方案；极端大包可再按版本分散并建包级目录；不固定一生态一分片 |
| 图集、季集、课程组成 | 局部成员分页与更新，受控穿透 | 按拥有对象／结构组织；超大结构按既有报告进行分段与投影，不每次全量装载 |
| 历史、采集观察、测量 | 按对象与时间读取、增量写入、按保留期维护 | 时间段和对象桶按查询组合；事实历史与可过期运行记录分别定义保留策略 |
| 跨领域筛选与反向关系 | 精确关系条件和全文联合执行 | 单库阶段索引联接；迁出前证明共置、投影或有界跨片查询的等价性与成本 |

表组独立不等于同实例资源隔离。CPU、I/O、WAL、连接与内存仍共享；分区也不自动成为跨机器分片。PostgreSQL 的分区裁剪、唯一约束及分区数量都限制具体设计；不能仅增加分区数就宣称查询更快。[PostgreSQL 分区设计](https://www.postgresql.org/docs/18/ddl-partitioning.html#DDL-PARTITIONING-DECLARATIVE-BEST-PRACTICES)

### 6.3 交付前尚需的证据

沿用总体报告的起始测试画像：100 次／秒混合读取、20 次／秒前台修改、50 对象／秒来源处理、32 并发客户端及 5 倍突发。它是候选测试输入，不是容量承诺；接入包、媒体或商品时，重新给出实际查询比例、单对象放大、延迟目标和来源刷新期限。

每个启用表组的实施方案至少记录：

- 5 亿／30 亿行下的对象、子行、历史、来源和投影数量；平均与高分位扇出、热点分布及删除／更新率。
- 读写速率、并发、p95／p99 或吞吐目标、游标分页、单请求扇出与执行预算；避免外层 LIMIT 掩盖内部无界工作。
- 行及索引实测宽度、写放大、WAL、缓存工作集、跨组网络量；导入与回填的有界批次、队列上限及背压。
- 代表性数据分布下的 `EXPLAIN (ANALYZE, BUFFERS)`、更新／删除及索引落后行为；小样本通过不等于目标规模通过。
- VACUUM、索引重建、恢复和迁移窗口；磁盘／WAL 增长、队列年龄、尾延迟和热点等可观测阈值，以及阈值触发后的扩容或降载路径。

第一阶段仍是 1 台 RS4000＋1 台 RS8000 下的单库分表方向；本报告没有确认具体代际资源或验证完整长期容量。分区、分片数量及采购规格均待测定。两台机器不是容纳全部上述数据的永久上限，也不是已通过全域 5 亿／30 亿行验收的证据。

独立搜索不是此处的容量捷径。PostgreSQL 继续主导复杂关系与全文联合查询；迁出任何表组或全文能力之前，必须处理其关系查询代价，沿用[查询报告 §8](REZICS-内容结构关系与查询模型-20260906.md#8-多层查询与全文检索共同设计)的准入要求。

## 7. 实施分期与完成判据

**本节是依赖关系与交付检查，不是要求下一任务一次实施全部列表。未来领域的先后顺序尚未排期。**

| 阶段 | 进入条件与工作 | 明确不包含 |
| --- | --- | --- |
| 文档决定，本次 | 固定拆分规则、领域地图、状态标记及旧报告引用 | 代码、迁移、生产操作；不改变现有对象含义 |
| 现有能力重构，待实施 | 在明确任务范围内改进现有作品、身份、字段、关系和查询；保留单库事务 | GPU、算力、课程等全部未来表；预建所有分片或微服务 |
| 单个新领域启用，未来按需 | 用真实样本固定身份、核心字段、关系、来源和一个完整用户流程；只增加必要结构 | 因一个新类别而复制账户、社群、标签或百科系统 |
| 扩展分发能力，未来按需 | 有实际客户端／生态需求时交付包坐标、版本、依赖和发布协议 | 用通用 Package 类型宣称兼容全部包管理器或插件市场 |
| 容量扩展，待验证后实施 | 指标显示瓶颈，完成对应表组的分区／分片、回填和查询验证 | 按类别数平均分配数据库；未经等价性验证迁出关系或全文 |

新增一个语义类别时，可以只使用已有定义和模型；新增一个有行为的领域时，以下交付项必须在该领域的实施记录中逐项说明：

1. **身份与语义：** 同一对象判据、外部标识范围、版本和关系粒度、合并／删除行为、每项事实唯一归属。
2. **持久化契约：** 类型、约束、索引、私密资料边界、历史与恢复；真正的 Unit 扩展遵循主键／外键规则，通用 JSON 不替代这些保证。
3. **应用路径：** 创建、读取、修改、导入、导出、查询与必要能力覆盖；审查现有 `unit.kind`、历史分支、权限、API／SDK 等所有受影响边界。普通动态类不必新增协议 kind。
4. **范围内的用户价值：** 目标对象能被识别、发现、收藏、讨论或使用；评分、Issue 与安装等只开放已经实现且语义适用的能力。
5. **增量与迁移：** 有界回填、单一权威写入端、冲突与幂等、修订和投影版本、失败恢复；跨库时另行完成写入围栏和路由切换，不承诺只改连接字符串。
6. **验证证据：** 真实来源样本和反例、必要契约检查、代表性查询与容量预算；前端验收遵循仓库规则，不以静态检查代替用户体验验收。

示例验收必须能够区分：显卡型号与实物；课程与开课；同内容的两次发布；软件项目与两个注册表坐标；服务规格与运行采样；AI 模型与其推理服务。对同一个对象添加规格，不产生第二份身份或相互独立的当前值。

持久化或公开契约改变遵循 v1.0.0 兼容基线与 RomVer，发布过的迁移保持不可变，通过前向迁移交付；不恢复 pre-v1 结构。相关能力完成后，在对应实施文档记录实际契约和证据，再更新本文 §1.1 的状态，保留尚未交付的范围标记。

## 8. 证据与产品边界

本报告采用成熟系统和标准来校准身份与结构，而不是宣称存在一套现成、唯一正确的全领域数据库 schema。标准语义不等于 SQL 设计，研究和示例也不等于 REZICS 的容量测试。

跨领域／跨生态索引已有实践：Wikidata 组织多领域结构化知识，deps.dev 聚合多个包生态的包、版本与依赖。[Wikidata 简介](https://www.wikidata.org/wiki/Wikidata:Introduction)、[deps.dev 文档](https://docs.deps.dev/)

这些实践支持通用索引方向，但不保证世界范围的完整收录、持续准确更新或商业成功。REZICS 对外应明确每个已接入领域的覆盖、来源与更新质量；融资与增长仍需证明收藏、讨论、百科贡献和实际使用形成持续价值。新领域应能复用这套能力，并只扩展自己消耗的数据与计算，而不是重新建立一套割裂的平台。
