## Why

Persistent list ordering should use `position` Fractional Indexing instead of
numeric `sortOrder`. Numeric ranks force adjacent rows or whole lists to be
rewritten for insert/reorder operations, while fractional positions preserve the
same read semantics and enable single-row moves with btree-friendly ordering.

This is a development-stage cutover. There is no compatibility layer and no old
`sortOrder` DTO/API surface for persisted rank fields.

## Durable constraints & decisions

- (type) Persisted rank fields are named `position` and are strings generated by
  the existing Fractional Indexing helpers.
- (comment) Schema and contract rank fields carry `// Fractional Indexing` so
  future readers do not reinterpret them as numeric display positions.
- (test) Ordered reads use `position` with a stable tie-breaker where the table
  can contain equal positions.
- (test) Batch writes derive evenly spaced fractional positions from request
  order when callers do not supply one.
- (comment) Directional query variables such as `"asc" | "desc"` are not rank
  fields and may remain named `sortOrder`.
