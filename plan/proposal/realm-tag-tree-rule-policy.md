## Why
Realm tag navigation and realm rules are still partially modeled as Realm-owned
profile fields. `Realm.extra.tagTree` / `tagView` describe a realm taxonomy over
global tags, but they are not low-level profile extras and should not carry
inline multilingual label data. Realm rule fields on `Realm` similarly mix
community identity with governance policy, acknowledgements, and presentation.

This change promotes both concerns into explicit domains. Realm tag tree becomes
a first-class versioned tree document whose nodes are either global tag
references or label nodes. Policy-tag data remains table-backed and independent;
the app joins policy status onto the tree for management UX. Realm rules become
a policy/revision/item model where each rule item points at one POST Unit for
i18n content, and dock/rule-page renderers show Reddit-style per-rule
expand/collapse views.

## Durable constraints & decisions
- (type) `RealmTagTree` is the domain name. Do not call it layout; `flat`,
  `grouped`, and `tree` are view modes that project the same stored tree.
- (type) Realm tag tree storage is a first-class versioned envelope:
  `schema: "rezics/realm-tag-tree"`, `version: 1`, `view`, and `nodes`.
- (type) Realm tag tree nodes are explicitly typed as `kind: "tag"` or
  `kind: "label"`. There is no `group` node kind.
- (type) Realm tag tree nodes do not have durable node IDs. Tree edits replace
  the whole envelope; temporary frontend keys are local UI state only.
- (type) Tag nodes reference global TAG Units through `tagUnitId`. The realm
  never owns tags.
- (type) Label text uses LABEL Unit references. Do not keep or add inline
  `label`, `labelTranslations`, or other multilingual label payloads in the
  tree JSON.
- (type) `querySource: "normal" | "policy"` belongs only to tag nodes. It
  selects stream/search behavior; it does not embed policy data in the tree.
- (test) Server validation rejects unknown node kinds, duplicate/malformed
  envelope data, inline labels/translations, `querySource` on label nodes,
  missing TAG Units, and missing LABEL Units.
- (test) Realm tag tree reads do not require policy-tag tables. Policy data is
  fetched separately and joined by `tagUnitId` in app management UI.
- (comment) Policy-tag remains the data/query layer for governed tag lists:
  `PolicyTagRule` and `PolicyTagApplication` must not depend on tree nodes.
- (type) Realm rule policy is not stored on `Realm`. A realm has a
  `RealmRulePolicy` that points at the current immutable revision.
- (type) A rule revision owns ordered rule items. Each rule item references one
  POST Unit (`rulePostUnitId`) as the localized rule content carrier.
- (type) Rule item identity is the rule item row generated by Postgres UUIDv7;
  frontend clients do not generate durable rule IDs.
- (test) Rule acknowledgements bind to the current rule policy revision, not to
  `Realm.ruleUnitId` or dock widget configuration.
- (test) Dock `rules` widgets render the realm rule policy and never own a
  second rule pointer.
- (test) Rule page and dock summary render ordered rule items with independent
  expand/collapse state, using the requested language fallback chain for each
  rule POST.

## Out of scope
- Replacing policy-tag tables with tree data. Policy-tag remains the independent
  governance/query layer.
- Fully normalizing realm tag tree nodes into relational rows before there is a
  server-side subtree query requirement.
- Adding durable frontend-generated UUIDv7 IDs for tag tree nodes. Tree node
  identity is not persisted; Postgres remains the source for durable UUIDv7 row
  IDs.
- Changing global tag ownership semantics. Tags remain global Units, and realms
  only organize or label references to them.
- Building a general page builder or changing dock composition beyond rendering
  the rule widget from the new rule policy.
